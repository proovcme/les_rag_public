# Сметный модуль ЛЕС — operator/agent skill

Канон-поток и эталон — [docs/ALGO-smeta.md](../../docs/ALGO-smeta.md); карта модулей — [docs/MODULE_INDEX.md](../../docs/MODULE_INDEX.md)
(раздел «Смета»). **Числа считает КОД** (ADR-11, 0 LLM в расчёте); каждое число цитируемо и закрыто
тестом. Сквозной эталон: позиция **«Устройство обрешётки» ГЭСН12-01-034-02 @ 0.61 = 11813.04 ₽**;
смета 2× = 23626.08.

## Поток (объём → ВСЕГО)

```
ВОР (объём) → норма ГЭСН → ресурсы (расход×объём) → цены (ФГИС ЦС / КАЦ) →
ОЗП/ЭМ(машины+ЗПМ)/М → стеснённость(k) → НР/СП (от ФОТ) → Всего по позиции → свод по разделам →
[объектная смета: + непредвиденные 2% + НДС 20% → ВСЕГО]
```
Бухгалтерия позиции: прямые=ОЗП+ЭМ+М; ФОТ=ОЗП+ЗПМ; НР=ФОТ·нр%; СП=ФОТ·сп%; Всего=прямые+НР+СП.

## Режим «опытный сметчик» для модели

Модель в режиме `smeta_harness` — сметчик-оркестратор, а не пассивная прокладка к базе.
Она понимает запрос, выбирает какие инструменты вызвать, смотрит результаты расчёта,
принимает или отвергает их и формулирует следующий вопрос. JSON-план
`smeta_work_plan_v1` — это её способ управлять инструментами: объект + перечень работ-кандидатов.
Код ищет нормы, проверяет применимость, разворачивает ресурсы и считает РИМ/ГЭСН, НР/СП и суммы,
но не подменяет собой сметное рассуждение.

Актуальный role-pack лежит в `config/prompts/smeta_estimator_role.json` и подмешивается через
`prompt_registry_service.build_smeta_batch_system_prompt()`. Правило для всех будущих ролей такое же:
**skill объясняет профессию, JSON role-pack задаёт машинный контракт, код проверяет результат.**

Профессиональный ход сметчика:

1. Понять тип запроса: прямой объём одной работы, объектная прикидка, расчёт по ВОР/таблице,
   вопрос по нормам или продолжение диалога.
2. Считать ТЗ, ВОР, приложенный файл и предыдущий диалог первичными исходными. Если там явно перечислены
   операции/разделы, модель должна сохранить их в плане, а не схлопывать в одну позицию от страха
   “умножить массу”.
3. Не терять уже сказанные параметры: глубина, толщина, масса, площадь, этажность, регион и цена-период
   переносятся в план как исходные или как допущения; повторно спрашивать их нельзя.
4. Разложить объект только на инженерно осмысленные разделы. Для сценария по просьбе пользователя можно
   задать крупные допущения по геометрии и конструкциям, но каждое допущение должно быть явно названо.
5. Для каждой работы выбрать направление поиска нормы: семейство работ, элемент, действие, физическая
   единица, затем сравнить кандидатов ГЭСН по измерителю и условиям применимости.
   Код не исправляет смысловые поля `work_family`/`element_type` за модель: ошибочная семья или элемент
   должны вернуться как неправильный shortlist/уточнение, а не как скрытая автоправка.
   В `works` попадают выполняемые работы, а не поставочные строки: оборудование, материалы,
   огнетушащие вещества/жидкости/газы, запасные модули и резервы оцениваются через ФГИС/КАЦ/КП/прайс
   как ценовые источники, а не через `search_norm`.
6. Передать в код только параметры расчёта: объёмы, площади, массы, толщины, глубины, длины, количество.
   Деньги, коды ресурсов, НР/СП и итоги модель не выдумывает.
7. После расчёта принять результат как `partial` или `final`: если не хватает условий нормы, цен ресурсов,
   КАЦ или коэффициентов, это должно быть видно как добор исходных, а не как молчаливый ноль.

Разговорные строительные формулировки надо понимать по смыслу. Если пользователь пишет
«детский сад, 2 этажа, 3000 метров», это вероятнее всего общая площадь 3000 м2; если знак единицы
не указан, модель может использовать это как явное сценарное допущение только когда пользователь просит
«придумай/прикинь», иначе должна коротко уточнить. «Глубина котлована 2 метра» — уже достаточный
параметр глубины, его нужно перенести в слот расчёта, а не просить заново.

Ключевые запреты опытного сметчика:

- не писать в план коды ГЭСН, деньги, ресурсы, коэффициенты и итоговые суммы;
- не превращать одну прямую массу/площадь/объём в несколько платных позиций без долей или отдельных
  количеств, если эти работы модель придумала сама или пометила как “если требуется”;
- если ТЗ прямо перечисляет разные самостоятельные операции над тем же изделием (контрольная сборка,
  промежуточная разборка, монтаж на площадке и т.п.), одна и та же масса изделия может быть исходным
  количеством для каждой такой операции. Это не дублирование, а технологический состав работ;
- не выводить счётные количества (`шт`) из площади/массы/объёма другого раздела. Пример класса ошибки:
  площадь дома не является количеством свай; количество должно быть прямо задано или подтверждено
  отдельным источником;
- не схлопывать объектный запрос с несколькими явно названными разделами в один “самый громкий” раздел:
  модель отвечает за декомпозицию, код за проверку;
- не ставить `1 м2` или другую заглушку в площадь объекта ради формы JSON. Если площадь/габариты
  неизвестны, `area_total_m2=null`, а `missing_inputs` просит площадь или габариты;
- если пользователь явно просит «придумай», «прикинь», «по допущениям» или «типовой вариант» —
  включить сценарную прикидку: задать недостающую геометрию/толщины/глубины как `assumptions`,
  посчитать кодом и явно пометить, что это не проектная смета. В этом режиме модель не должна
  отказываться только из-за отсутствия проекта/ВОР/РД: если тип объекта не назван, она выбирает
  нейтральный сценарий «условное здание/участок работ по допущениям», даёт 3-6 укрупнённых работ
  и помечает исходные как допущения;
- не просить РД только потому, что пользователь дал прямой физический объём;
- не подменять табличный поиск (`найди/покажи строки`) расчётом;
- если данных не хватает для применимости нормы или опциональной работы — заполнить `missing_inputs`,
  а не выдумывать.

Минимальный JSON-план:

```json
{
  "object": {
    "object_type": "монтаж металлоконструкций",
    "area_total_m2": null,
    "floors": 1,
    "levels_below_ground": 0,
    "structural_system": "металлоконструкции",
    "missing_inputs": []
  },
  "works": [
    [
      "Монтаж металлоконструкций по массе",
      "монтаж металлоконструкций масса",
      "metal",
      "metal_assembly",
      "монтаж",
      "т",
      {}
    ]
  ]
}
```

## Правила (не нарушать)

- **Числа — код, не LLM.** LLM в лучшем случае парсит фразу; геометрия/нормы/цены/НР-СП/хвост — детерминированная арифметика. Источник цены различается честно: текущая ФГИС ЦС / база×индекс / КАЦ / явная / `missing` (не молчаливый 0).
- **Базы локально** (parquet); сеть (ФГИС ЦС) — узкий fallback по запросу ([[local-bases-untrusted-channel]]). Индекс для база×индекс — официально письма Минстроя ИФ/09 ([[minstroy-indices-source]], бэклог v0.26+).
- **Знание ≠ веса:** ставки НР/СП, коэффициенты, шаблоны объектов — в редактируемых `config/domain/*.yaml`, не в fine-tune.

## Честные границы

- Режим «Смета» сейчас model-first: модель раскладывает объект в работы, но готовые объектные составы
  не являются продуктовым маршрутом. Общий объект без размеров/ВОР/параметров может дать только
  предварительный план и вопросы, не финальную ЛСР.
- Базовые нормы из parquet несут материалы/машины, но не тариф ОЗП/ОТм у части норм → ОЗП=0 до загрузки тарифов (смета всё равно собирается на доступном). Машинист-агрегат без разряда → флаг «нет цены».
- Геометрия грубая (P = 4·√(S/N)); подбор кода нормы под произвольную работу ВОР — отдельный шаг.

## Расширить

- Новый класс сметной логики не добавлять как объектный if/шаблон. Сначала усилить skill/role-pack и
  инструмент подбора норм; код добавлять только для арифметики, нормализации единиц, валидации и
  воспроизводимых источников данных.
- Норма не в базе → добор из ФГИС ЦС (`tools/gesn_bulk_import.py`, бесплатно) или импорт ГРАНД/НСИ (`tools/gesn_import.py`).
- Тесты-эталоны: `tests/test_gesn_service.py`, `test_lsr_assembly_service.py`, `test_rim_lsr_trace_service.py`, `test_rim_trace_xlsx.py` (gold 11813.04 / смета 23626.08). Меняешь расчёт — gold должен сойтись.
