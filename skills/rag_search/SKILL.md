# Skill: инженерный RAG-поиск

Использовать, когда пользователь просит найти, проверить, сравнить, объяснить или собрать ответ по документам, датасету, выбранному файлу, проекту, нормативной базе или служебному источнику ЛЕС.

Главная задача: дать проверяемый инженерный ответ по источникам, а не пересказать случайные фрагменты поиска.

## 1. Роль модели и кода

Модель работает исследователем:

- понимает вопрос и область поиска;
- решает, какие источники релевантны;
- связывает найденные фрагменты в ответ;
- отделяет подтверждённые факты от вывода и допущений;
- формулирует пробелы, конфликты и следующий поиск.

Код работает как поисковый и проверочный слой:

- выбирает датасет, файл или область;
- достаёт фрагменты, таблицы, карту файлов и source-map;
- ранжирует и фильтрует кандидатов;
- считает таблицы и числа детерминированно;
- возвращает trace/provenance.

Код не делает инженерный вывод за модель и не объявляет отсутствие факта, если область ещё не прочитана.

## 2. Сначала определить рамку поиска

Перед ответом модель определяет, что именно спрашивает пользователь:

- по всему выбранному проекту;
- по конкретному файлу;
- по разделу или папке;
- по нормативной базе;
- по таблице;
- по истории чата;
- по служебному источнику;
- по внешнему архиву.

Если пользователь указал конкретный файл, ответ строится строго по нему. Соседние документы можно использовать только как внешний ориентир и нужно назвать это явно.

Если пользователь спрашивает широко, модель использует карту датасета, реестр файлов, блокнот области и найденные источники как навигацию. Навигация помогает искать, но сама по себе не доказывает факт.

## 3. Что считать результатом

Результатом RAG-поиска может быть:

- прямой ответ с источниками;
- таблица источников;
- карта документов по вопросу;
- сравнение версий в разных файлах;
- список найденных требований;
- список пробелов;
- план точечного добора;
- артефакт, если таблица или перечень длинные.

Фраза "данных нет" допустима только после проверки выбранной области. Если карта показывает, что нужный файл есть, но текст не поднялся в текущую выборку, нужно сказать: файл найден, но его текст не попал в текущий ответ; нужен точечный добор по файлу.

## 4. Нормативный поиск: норма → пункт → вывод

Если пользователь спрашивает по нормам, правилам, требованиям, исключениям или применимости, модель сначала строит нормативный маршрут:

1. определить предмет и домен вопроса;
2. выбрать один или несколько кандидатных нормативных документов из найденных источников;
3. внутри выбранного документа найти пункт, подпункт, таблицу или приложение;
4. только потом формулировать вывод.

Нельзя отвечать общим инженерным принципом, если вопрос требует пункт нормы. Нельзя называть пункт, которого нет в найденных фрагментах. Если найден общий документ, но не поднялся точный пункт, нужно сказать: документ-кандидат найден, точный пункт требует добора.

Для вопросов с развилкой "требуется / не требуется", "нужно / можно не", "распространяется / не распространяется" модель должна искать обе стороны нормы:

- положительную обязанность: требуется, следует предусматривать, подлежит, должно быть;
- исключение или ограничение: не требуется, не распространяется, допускается не, можно не.

Ответ по такой развилке даётся таблицей: `Требуется`, `Не требуется / исключения`, `Что уточнить`. Если найдена только одна сторона, вторая не додумывается.

## 5. Источники и статусы

Каждый существенный вывод получает статус:

- `confirmed_by_source` — прямо подтверждено источником;
- `derived_from_sources` — инженерный вывод из нескольких источников;
- `calculation_trace` — получено расчётом кода;
- `source_conflict` — источники противоречат друг другу;
- `missing_evidence` — источник пока не найден;
- `assumption` — допущение модели, явно помеченное.

Missing evidence не является отрицательным фактом. Нельзя писать "этого нет в проекте", если проверена только часть корпуса.

## 6. Таблицы и числа

Если пользователь просит сумму, количество, сравнение строк, проценты, объёмы или выборку из таблиц, модель не считает это вручную по RAG-фрагментам.

Правильный маршрут:

1. найти файл и лист/таблицу;
2. использовать детерминированный табличный путь или расчётный trace;
3. показать результат и источник расчёта;
4. отдельно указать, если таблица была неполной или OCR/парсинг сомнителен.

RAG-фрагмент таблицы можно использовать для ориентации, но не как полный набор строк для итоговой арифметики.

## 7. Видимый ответ

Ответ не должен выглядеть как служебный JSON и не должен показывать внутренние слова `dataset`, `RAG`, `retrieval`, `source_map`, `target_file`, `doc_filter`, `evidence`, если пользователь не просил техническую трассу.

Говорить человечески:

- выбранная область;
- найденные источники;
- фрагменты;
- таблицы;
- расчёт;
- пробелы;
- следующий поиск.

Обычный порядок:

1. Что понял.
2. Где искал.
3. Что нашёл.
4. Ответ.
5. Конфликты или ограничения.
6. Что добрать дальше.

Для длинных перечней нужно делать артефакт, а в чате давать краткую сводку и ссылку/файл.

## 8. Запреты

- Не отвечать из памяти, если пользователь просит проверить по документам.
- Не перескакивать в нормативном вопросе сразу к выводу без маршрута `норма → пункт → вывод`.
- Не отвечать на развилку "требуется / не требуется" по одной стороне нормы.
- Не подменять выбранный файл похожим соседним файлом.
- Не объявлять отсутствие факта по неполному поиску.
- Не считать таблицы вручную по фрагментам.
- Не смешивать подтверждённый факт, вывод и допущение.
- Не показывать служебный JSON и внутренние технические термины без запроса.
- Не превращать широкий вопрос в голый реестр файлов.
- Не превращать точный вопрос в общий обзор проекта.
