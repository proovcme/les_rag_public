# ADR-15 — Модель → RAG → результат модели → расчёт и XLSX

T119.9 / 0.30.130: снятие ресурса нормы — решение модели с доказуемой диспозицией.
`replaced_by` связывает снятие с поставкой изделия той же исходной строки (количество больше
нуля, одна поставка — один ресурс) либо объявляет `not_required` с обоснованием. Код проверяет
адресуемость, связь и наличие количества, но не выбирает изделие и не приравнивает количества.
Пустая выдача поиска признаётся только при статусе выполнения в трассе retrieval.

T119.9 / 0.30.129: учёт строки и исполнение операции разделены. Строку учитывают работа
по норме, самостоятельный материал и распределение в ресурс; снятие ресурса — исполненный
модификатор, который строку не учитывает. Снятие без поставки изделия той же строки и
второе действие над тем же ресурсом отклоняются. Выполненный поиск без совпадений — ответ
модели, а не отказ прохода; отказом остаются неготовый сервис и пустой запрос.


T119.9 / 0.30.128: модельный учёт ресурсов получил снятие. `included`
распределяет количество существующего ресурса, `excluded` снимает названный материал
нормы, самостоятельный материал добавляет позицию. Без снятия проектное изделие рядом
с материалом нормы давало двойной учёт покрытия. Снятие — решение модели: код проверяет
только адресуемость (родитель однозначен, ресурс есть в составе этой нормы и это
материал) и не выбирает, что снимать. Норма, состав работ и прочие ресурсы не меняются.

T119.9 / 0.30.125: неуспешный model-requested поиск ранее возвращал внутренний
`error=MODEL_RAG_SEARCH_INCOMPLETE`, который public error boundary скрывал как
`MODEL_SERVICE_UNAVAILABLE`. Теперь `model_rag_failure_detail` формирует
`code`, читаемый `detail`, `blocked_queries` (1-based номера) и `query_failures`
(статус, операция, коллекция, error_code/reason). Ограниченная диагностика
сохраняется в серверном предупреждении и HTTP/SSE. Сырой trace, текст запросов
и исключений не переходят эту границу. `missing/no_matches` отличим от
`blocked/retrieval_not_ready`; в этой версии оба по-прежнему останавливают
проход. Это исправление наблюдаемости, не доказательство причины живого 503
и не принятие нормы или сметы.

T119.8aa / 0.30.122: терминальный структурный отказ сохранялся в append-only
feedback, но не давал очередь следующим исходным строкам: нет packagable
decisions — следующая порция снова первая. Теперь тот же event содержит
серверные portion_shown. observation_order читает только эти якоря; старые
events без metadata не превращаются в вымышленные просмотры по неверным
model source_row. Идентичность session/source revision и идемпотентный turn_id
сохраняются. last_observed_pass — очередь рассмотрения, не completed/attempts
и не подстановка решения. Сначала ещё не рассмотренные строки, затем открытые
в порядке давности; после полного обхода ни одна не закрывается автоматически.
for_anchors возвращает последние ошибки текущих строк, не требует пересмотра
чужой порции и не удаляет исходные rows/raw_answer/errors/evidence. Новый
успешный event снимает старую подсказку только со своих строк. Отказавший
провайдер без терминального ответа просмотром не становится. Нормы/количества/
ресурсы/коэффициенты не меняются; непринятые ответы не входят в расчётную
проекцию. Изменение совместимо с существующей SQLite-схемой: используется
дополнительное поле существующего evidence_json, старый runtime его игнорирует.

подтверждает доставку существующего описания при длинном resource_preview.

T119.8t / 0.30.116: поздняя проверка текущей порции согласована с общей структурой
нескольких операций. Один source anchor допускает повторение только при явном

поэтому слияние aliases без этой проверки могло бы потерять часть evidence/состояний.
Модель получает причину отказа и может повторить одинаковый source_row; код не меняет
её строки, нормы, количества или resource review. Отсутствующие/чужие/неоднозначные
anchors, unnamed дубли и duplicate work_id не разрешены. Actual chat regression
до исправления2FAIL/1PASS: обе именованные операции отклонялись seen_anchors.
После исправления проверяются переданные в workbook решения и раздельные evidence
snapshots в cursor. Это не профессиональная приёмка правильности норм модели.

T119.8s / 0.30.114: очередность не зависит от совпадения причины отказа. План
сначала берёт строки без сохранённого модельного решения, затем открытые строки
по возрастанию last_decision_pass. Это номер успешно сохранённого ответа по строке,
а не подтверждение правильности. Только подтверждённые расчётом строки исключаются
из очереди; attempts/exhausted остаются прежней диагностической историей.
Ресурсный receipt/ошибка возвращается при следующем рассмотрении строки; это может
быть после новых строк. Старые решения и сырые ошибки не теряются во время ротации.
SQLite additive migration last_decision_pass INTEGER NOT NULL DEFAULT 0 не меняет
decision_json, нормативные решения, цены, количества, состояния или attempts.
Для старых записей0означает отсутствие исторического номера хода; новые ответы
сохраняют номер passes+1 в той же транзакции. Повтор pass_id не меняет очередность;
пересчёт уже сохранённой книги не является новым ответом и не меняет last_decision_pass.
Старый runtime может читать прежние колонки после rollback без удаления новой колонки.
До исправления replay changing-diagnostic за6ходов показывал7из70строк при0closed.
Тест проверяет полный повторяемый цикл без закрытия строк и без требования одного
и того же текста ошибки. Проверка реальной модели и полного XLSX остаётся отдельной.

## Контекст

Живая Qwen 3.5 9B показала достаточный рабочий контур на реальной ВОР: модель
сама сформулировала запросы, сметный RAG вернул карточки выбранного датасета, та же
модель выбрала нормы, а штатный адаптер ЛЕС рассчитал и оформил XLSX.

Отказы создавались не моделью и не RAG, а промежуточной обвязкой: обязательными
JSON-планами, специальными status/decision-вызовами, фиксированным числом ходов,
повторными подтверждениями и потерей исходного вложения перед финальным вызовом.
Изолированные тесты эти пользовательские отказы не обнаружили.

## Решение

Активный путь один:

```text
исходный вопрос + полное вложение + явно выбранный датасет
  → та же модель формулирует любое необходимое число RAG-запросов
  → код буквально исполняет запросы через настроенный dedicated сметный RAG
  → код группирует profile-owned число карточек на запрос как Qx.Hy и сохраняет все группы
  → та же модель видит исходный ввод и весь возвращённый evidence
  → модель обычным текстом выдаёт все профессиональные строки и решения
  → код механически читает строки из ответа, не меняя сам видимый ответ
  → код проверяет структуру/единицы/provenance, подставляет цены, считает
  → ЛЕС автоматически прикладывает XLSX к ответу
```

Число строк и запросов не ограничивается предметной константой: 7, 19, 30 или
иное фактическое количество обрабатывается одним и тем же контрактом.

До терминального результата модели код имеет право только:

- разрешить явно выбранный dataset scope;
- предоставить read-only RAG и буквально исполнить запросы модели;
- вернуть evidence с координатами и сохранить trace;
- прервать только технически бесконечное исполнение.

До терминального результата модели код не имеет права:

- выбирать или переписывать запросы, нормы, аналоги, coverage и статус решения;
- заменять исходный файл сводкой или терять его перед финальным вызовом;
- требовать специальный JSON-план как допуск к RAG;
- требовать JSON/schema или model tool-call для итогового ответа;
- навязывать R1/R2-review, mapping lock, подтверждение привязки или фиксированное
  число ходов/строк;
- считать обычный текст модели ошибкой протокола и поэтому не пускать её в RAG.

Для estimate-профиля имя сметной коллекции берётся из active base/runtime
configuration и может быть любым. Общий `les_rag` не является fallback: если
dedicated dense+sparse native RRF не готов, поиск блокируется явно, чтобы
смешанный пользовательский корпус не маскировал ошибку маршрутизации.
Model-authored query является инвариантом estimate workflow и применяется к
старым keep-state user-profile snapshots без изменения их prompt/skill.
Только профиль `estimator` маршрутизируется в карточки ФСНБ; обычный профиль с
model-authored запросами остаётся в явно выбранном пользовательском dataset.
Внутренний retrieval для одного запроса делает широкий native-RRF overfetch,
удаляет только точные дубли и ограничивает долю одного физического документа,
после чего передаёт profile-owned число результатов (заводской default 6).
Пул в 256–512 model-facing hits не создаётся. На этом bounded-пути также
не запускается document-router: каждый запрос модели сразу идёт в native RRF,
без отдельного JSON/LLM-вызова и без скрытого предварительного отбора документов.

После терминального результата модели код обязан послушно сохранить её выбор и
может выполнять только детерминированную работу: проверить ссылочную структуру,
совместимость единиц и provenance, получить цены ресурсов из выбранной либо
системной Сплит-формы, посчитать итоги и сформировать XLSX. Найденные конфликты
показываются в результате, но не дают коду права тихо изменить или удалить
решение модели.

Перед XLSX выполняется одна локальная проверка ссылочной целостности. Она не
вызывает модель повторно и не создаёт новый workflow-шаг: проверяются только
полнота `source_row`, отсутствие дублей, существование `Qx.Hy` и принадлежность
переданного `norm_code` указанной карточке. Проверка ничего не исправляет; при
ошибке она запрещает только ложный XLSX. Значения `source_row` и `norm_code`
парсер и расчётный адаптер больше не перенумеровывают и не вырезают регулярным
выражением. Конфликты упаковщика сохраняются рядом с готовым XLSX как `partial`,
а не маскируются внешним статусом полного успеха.

Если датасет не выбран, ЛЕС работает как обычный AI-harness без неявного RAG.

## Приёмка

### Порции ведомости: текущее состояние 2026-09-10

Обновление 2026-09-11: контракт ответа задаёт десять колонок Markdown и разделитель
с десятью ячейками. Тест берёт оба из production-контракта; прежний тест сам достраивал
корректный разделитель и не замечал ошибку инструкции.
Реализованное в `fed2f406` закрытие после двух пустых норм не подтверждает полноту
сметного решения: оно не различает окончательный отказ модели и нехватку evidence.
Эта граница и повтор упаковки остаются открытыми — см.
[ревью 55aa521f](audits/SMETA-REVIEW-2026-09-11-55aa521f.md).

Для распознанного табличного вложения активный путь использует `smeta_portion_context`
до сборки запросов и ответа. План берёт до 25 ещё не закрытых строк в исходном порядке;
строка без нормы возвращается, а закрытые позиции не занимают следующее окно.
Это изменение прежнего полного-вложения baseline требует отдельной живой приёмки.

`vor_rows` сохраняет исходные строки, шапки каждого листа и разделы; ревизия включает
их содержание, но не имя файла. В многолистовой порции модель получает идентификаторы
`лист!позиция`. Неоднозначный номер не сопоставляется с первым подходящим листом.
`PortionCursorService` хранит последние ответы по строкам отдельно от признака закрытия.
Повторный ответ может заменить норму или вернуть строку в незакрытые, без изменения
самих решений кодом. Старые XLSX-ревизии остаются в artifact store.

`merged_pass_decisions` собирает книгу из накопленных и текущих решений в порядке
исходной ведомости. Структурно некорректный ответ не записывает прогресс. Явные маркеры
отсутствия нормы не закрывают строку. `attachment_retry` определяется числом реально
незакрытых строк после ответа, включая последнюю порцию. При открытии прежней cursor DB
автоматически добавляется `is_closed` (существующие записи считаются закрытыми);
расширение source revision начинает отдельный курсор для прежних вложений.

Проверки: `test_smeta_portion_review_regressions.py`, `test_smeta_portion_wiring.py`,
`test_portion_cursor_service.py` и сценарии `active_model_rag_portion_*` в
`test_chat_evidence_application_service.py`. Последние проходят настоящую функцию чата
с тестовым транспортом и SQLite, но не доказывают качество подбора живой моделью.

Минимальное доказательство строится на живом пользовательском пути, а не на
изолированном mock-тесте:

1. Пользователь прикладывает реальный файл и явно выбирает один датасет.
2. Trace показывает запросы, написанные моделью для всех фактических строк.
3. Финальный model-call одновременно содержит исходный файл и RAG evidence.
4. Та же модель возвращает все строки без фиксированного лимита.
5. ЛЕС в том же ответе автоматически выдаёт рассчитанный XLSX.
6. Если подключена Сплит-форма, графы цен заполнены кодом с provenance; пробелы
   и конфликты видны и не переписывают модельный выбор.

Живая приёмка 2026-09-01 на изолированном dev proxy `8060` прошла с реальным
PDF: 19 строк/2366 символов без обрезки; Qwen 3.5 9B сформировала 11 запросов;
RAG вернул 11 групп по 6 карточек; answer context включил 6 блоков вложения и
все 11 evidence-групп без evidence omission; Qwen вернула 19 строк с 19
`norm_code` и 19 ссылками `Qx.Hy`; код самостоятельно вызвал упаковщик. Итоговый
XLSX содержит 17 `bound`, 2 `unit_conflict`, штатную базу цен Санкт-Петербурга
за II квартал 2026 года, 395 формул и формульную рассчитанную часть без НДС
3 564 688,87 руб. Установленные `8050/8051` не менялись.

Перед любой правкой chat/RAG/estimate автор обязан ответить «да» на три вопроса:

1. Финальная модель видит исходный ввод и возвращённый evidence одновременно?
2. Между моделью и RAG нет кода, принимающего профессиональное решение или
   запрещающего доступ из-за собственного orchestration-протокола?
3. Живая приёмка доказывает пользовательский ответ и файл, а не только зелёные
   внутренние тесты?

## Следствия

- `build_lsr_workbook_from_decisions` является пост-модельным адаптером, а не
  сметным мозгом.
- Автоматическая выдача XLSX и подключение pricebook входят в один
  пользовательский запрос; внешний ручной вызов адаптера является только
  диагностикой.
- Любая новая обязательная профессиональная стадия до результата модели требует
  нового ADR и прямого одобрения владельца.

### 0.30.92: обратная связь о структуре ответа

Нумерация поисковых строк снимается, точные повторы выполняются один раз;
исходный текст запросов остаётся в trace.model_queries_raw. Уникальные запросы
не ограничиваются по числу. Разделитель Markdown и пустые хвостовые ячейки
не меняют данные; непустое переполнение остаётся parse_error с raw_cells.
Отказы ссылочной/табличной проверки сохраняются в PortionFeedbackService,
отдельно от PortionCursorService.decisions: они не считаются попытками подбора,
не закрывают строки и не могут попасть в автоматическую пересборку XLSX.
Диагностика последнего ответа передаётся следующему вызову той же модели,
которая сама подтверждает или меняет выбор и текущие ссылки Qx.Hy. Событие
без ошибок снимает текущую подсказку, сохраняя историю. model_result_notice
доходит через HTTP/SSE и историю UI отдельно от неизменённого ответа.
Проверки: test_portion_feedback_service, test_chat_model_result_notice,
test_model_rag_partial_rows и сквозной test_chat_evidence_application_service.

0.30.93: практика и применение вновь предшествуют длинному перечню ресурсов.
Перестановка ресурсов в0.30.91 обрезала практику при том же бюджете; регрессия
проверяется в конечных messages test_resource_evidence_delivery_review.

В порции явно описан decision_kind=работа для выбранной нормы/аналога.
Это способ расчёта, а не товарная категория исходной строки. Не перечисляем

### 0.30.163: доставка доказательств и актуальность расчёта

Сохранённый чек не доказывает карточку нормы. `saved_norm_evidence` допускает повтор
только той же операции (source_row + work_id) и точного шифра по сохранённому
evidence_snapshot с явной отметкой доставки. Неоднозначный шифр отклоняется до
проверки истории. Старые снимки без этой отметки не переобъявляются доставленными:
для нового решения нужна свежая карточка. Прежняя родословная остаётся сохранена.

Каждая собранная книга обновляет статусы и чеки всех её исходных строк в курсоре,
включая строки вне текущей порции. Изменившийся чек переоткрывает проверку, не меняя
решение модели. CALCULATION_CONTRACT_REVISION входит в отпечаток свежести книги;
старые книги пересобираются штатным нулевым модельным вызовом перед продолжением.

Введённый в .144 лимит max(8, 4 * rows_in_pass) пока сохраняется как существующее
ограничение. Перечень отложенных запросов теперь находится в fixed evidence до
расчёта бюджета финального пакета; query_notice_delivered фиксирует реальную
доставку. Обрыв короткого списка по length тоже получает предупреждение. Это
исправление доставки, не доказательство оптимальности лимита или качества поиска.
Регрессии: test_smeta_evidence_reuse, test_chat_evidence_application_service.

### 0.30.164: явный отказ от нормы и проверяемый пакет

Чек предлагает сохранить работу без выбранной нормы как `decision_kind=уточнение`,
с прежними source_row/work_id и исходным объёмом. Вместо удаления незавершённой
операции модель сама очищает отвергнутую норму и её подтверждение в таблице.
Код не трактует пояснительный текст как команду изменить таблицу. Parser→merge→trace→XLSX
проверены регрессией: прежний шифр не восстанавливается, соседняя операция сохраняется.

`context_packet_trace` публикует SHA256/длину каждого объекта всех секций и каждого
сообщения `packet.as_messages()` с ролью. Текст request/profile/memory по-прежнему
скрыт. Проверка хеша против известного исходного текста отличает потерю входа от
редактирования приватной части трассы. Это отпечатки пакета данного этапа, не
перехват HTTP-запроса на стороне провайдера и не доказательство понимания моделью.
