# Проекты, чаты и явная память

Статус: 0.31.0 / build 706, dev candidate; не установлен и не опубликован.

## Навигация чата — 0.31.1

`chat_project_navigation.py::ChatProjectNavigation` показывает постоянный список
проектов на desktop и раскрываемый список на узком экране. Создание проекта
доступно согласно существующему admin permission; после создания открывается
первый чат, проект сразу появляется в списке. Под выбранным проектом видны его
чаты; «Без проекта» показывает обычные чаты, включая совместимую старую историю.
Переходы к Данных, Истории и Конфигурации сохраняются внизу списка. Мобильный
список закрывается при переходе к истории/данным/новому чату. UI не меняет scope
или владельца самостоятельно: все операции идут через `ChatWorkspace` с общим
busy/navigation guard. `on_change` обновляет список после commit и persist.
Память, файлы, вложения и все model/RAG/XLSX handlers остаются прежними.

## Пользовательский путь

Кнопка проекта в чате открывает обычный чат, список проектов и создание проекта
по названию. Новый проект сразу открывает первый чат; существующий — последний.
История внутри чата показывает только чаты текущего проекта либо обычные чаты.
Новый чат сохраняет принадлежность проекту, но начинает с его датасетов по
умолчанию. Область источников и выбранная роль сохраняются при отправке запроса.
Пока смена чата не завершена, другая смена и отправка запроса блокируются.
При смене очищаются временное вложение, поле ввода, прежний фильтр датасета,
target-file и открытые результаты. Реранкер снова выключен.

«Память» открывает общие предпочтения или записи текущего проекта. Пользователь
явно вводит запись, исправляет её, снимает «Использовать в ответах» и сохраняет
или удаляет. Автоматического заполнения в новых workspace-чатах нет.
Исторические автоматические заметки помечены; явное сохранение превращает их
в пользовательские записи. Общие предпочтения доступны всем чатам; проектные
записи — только чатам данного проекта. Память не является источником evidence.

## Хранение и API

`chat_session_service.py` добавляет `les_chat_sessions` в существующую MetaDB:
session_id, nullable project_id, title, role, scope_json, created_at, updated_at.
Принадлежность сессии неизменна. Старые history-сессии остаются обычными;
PATCH регистрирует такую сессию без вывода проекта из текста или датасетов.
Новые проекты используют прежние `les_projects`/`les_project_links`.
Датасеты проекта копируются как явные defaults; пустой проект означает
«Без источников», а не поиск по всем источникам.

`/api/workspace/sessions`: GET (project_id отсутствует — только обычные), POST.
`/api/workspace/sessions/{session_id}`: GET/PATCH роли, названия и области.
Создание принимает UUID, legacy session IDs продолжают читаться и обновляться.
Записи выполняются транзакционно; чтение не создаёт и не мигрирует базу.

`memory_service.py` расширяет существующие `les_notes` полями enabled и
source_session_id. `/api/workspace/memory` GET/POST, `/{id}` PATCH/DELETE
используют явный project_id (0 — общие предпочтения). Редактирование/удаление
проверяет область записи; ссылка на сессию — её существование и область.
Текст непустой, до 2000 символов. Все новые API требуют существующий require_user.
Это локальный пользовательский контур, не реализация многопользовательских ACL.

## Контекст локальной модели

Целевой диапазон — локальные модели 9–100B, облако опционально. Основной путь
проверяется на 9B. `resolve_session_memory_scope` использует реальную принадлежность
зарегистрированного чата; выбранный датасет другого проекта не меняет память.
Обычный зарегистрированный чат не получает LES.md через скрытый dataset→project
fallback. Старые незарегистрированные API-сессии сохраняют совместимость.

Зарегистрированные сессии рассматривают до 24 последних включённых явных заметок
своей области и общих предпочтений. SQL фильтрует scope/enabled/auto до LIMIT.
Заметки получают приоритет над навигационными объектами внутри memory projection;
при этом Governor сохраняет приоритет исходного вопроса и evidence во всём запросе.
Каждая запись входит целиком или исключается. Сериализованный payload ограничен
2500 символами, чтобы вместить полный текст 2000 символов и его служебные поля.

Query и final model calls получают заметки через существующий WORKING_MEMORY.
Новых model calls, summarization-loop, специальных планов и обязательного облака
нет. Исходный вопрос, полное вложение, evidence и решения модели сохраняются.
Trace содержит prepared/included/omitted IDs, а не содержимое памяти. Список
не претендует на перечисление записей за пределами bounded SQL-выборки.

## Проверки и границы

`WORKSPACE_TESTS` входит в `make verify`/`make test`: SQLite/API/миграция,
принадлежность и источники, edit/disable/delete, async navigation, model packets.
Активный model→RAG→result fixture проверяет память вместе с исходным вложением,
буквальными запросами модели и неизменным XLSX-пакетом.

Изолированный живой Qwen 3.5 9B probe, окно 8192: 4/4 — save/edit/disable/
обычный чат с выбранным проектным датасетом. Синтетический evidence quantity=17
сохранился; project tag изменился AMBER→COBALT→NONE, обычный чат вернул NONE.
Это проверка реального memory conditioning, не installed end-to-end приёмка.
В отдельном NiceGUI preview проверены создание проекта и note save/edit/disable,
полный компонент чата, общие зелёные токены кнопок/флажков. На ширине 390px
окна источников и памяти не дают горизонтального overflow (pageWidth=390,
диалоги в пределах 24..366px). `make verify`/`make test`: 1234 collected/passed.
Рабочий runtime и пользовательский корпус
не изменялись. Полная installed desktop/mobile приёмка остаётся перед выпуском.

Следующие отдельные этапы: новые формы ВОР/коммерческих смет, DOCX-шаблоны, vision.
Новый workspace не объявляет их реализованными.
