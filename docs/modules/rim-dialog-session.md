# Диалоговая РИМ-сессия

Статус: реализован dev-кандидат 0.27.3. Модуль расширяет `smeta_core`, не создаёт
второй сметный движок и не меняет профессиональные решения модели или сметчика.

## Поток

```text
XLSX/CSV
  → immutable source intake
  → ВОР revision
  → Qwen scope и batch catalog/search/read/submit
  → mapping revision → same-model global review
  → automatic monetary draft → optional user mapping lock
  → model/user-authored scenario либо canonical reviewed projection
  → canonical RIM calculator → requirements
  → КАЦ/коэффициенты/уточнения → обязательный пересчёт
  → priced draft → user final lock → XLSX + audit
```

Состояние хранится в `storage/rim_sessions` как SQLite-граф append-only
ревизий. Запрос с устаревшим `expected_parent_revision_id` отклоняется, сессии
изолированы по владельцу, а административный доступ остаётся явным.

Импорт ВОР сохраняет `visible_row_number:<n>` как служебную трассировку строки
источника, но не считает её blocker/assumption. Строка остаётся валидной, если
нет иных смысловых допущений; номер листа и строки продолжает входить в
`source_ref` и audit.

Долгий norm-mapping после каждого выполненного tool call и после каждой отдельно
принятой terminal-строки атомарно сохраняет
в `rim_agent_checkpoints` server-produced checkpoint: полный диалог, catalog /
search / opened-card trace, принятые строки, remaining `work_id` и следующий
ход. Checkpoint привязан к SHA-проверяемому payload и точной immutable
VOR-ревизии, но сам не двигает `head_revision_id`. После рестарта или timeout
агент продолжает с последнего tool result и не повторяет уже выполненный
поиск/чтение. После сохранения итоговой mapping-ревизии checkpoint удаляется.

Checkpoint доступен оператору через read-only
`GET /api/rim/sessions/{session_id}/mapping/progress`. Проекция не создаёт
ревизию и не меняет решения Qwen: для каждой строки ВОР она показывает
выбранный `base_type/collection`, число выполненных поисков, найденных
кандидатов и прочитанных typed-карточек, сохранённое решение и blocker
последней terminal-проверки. Решение от старой версии grounding contract
показывается как «нужна повторная проверка», а не как завершённое.

При resume Qwen получает один компактный authoritative snapshot: текущую фазу,
активный узел, видимых детей, причинно значимые ограничения и оставшиеся
`work_id`. Старые пары `assistant tool_call → tool result`, `last_3_events`,
полный path с описаниями и дублирующий state snapshot в модель не возвращаются:
они остаются только во внешнем checkpoint/event audit. Актуальный остаток
search/read/card/time budget принадлежит оркестратору и попадает в prompt лишь
тогда, когда влияет на допустимый следующий ход. Старое сообщение
`budget exhausted` не остаётся действующим после нового запуска.
Lifetime-счётчики сохраняются в checkpoint и финальном audit как неизменяемая
трасса, но новый bounded resume-slice получает собственный лимит: исторически
исчерпанный budget не превращает восстановление в тупик.
Одинаковая фаза нескольких строк должна исполняться одним batch-вызовом. Если
кандидаты уже есть, а карточки не открыты, следующий вызов по этой строке —
`read_norms_batch`, а не дальнейшее расширение каталога.

Завершённый typed-маршрут `family→collection→section→table` становится
`route_evidence_cache`. Он не применяется автоматически: Qwen сама вызывает
`reuse_norm_catalog_route`, указывает конкретный `cache_id` и объясняет применимость
для каждой новой строки. Код переносит только scope навигации; выбранная норма,
аналог и applicability не копируются, а обязательные search/read выполняются заново.

Повторное открытие уже прочитанной typed-карточки не расходует budget и
немедленно переводит Qwen к terminal-сериализации. То же происходит при
исчерпании текущего slice либо повторе идентичного tool call: выполненный
evidence не гоняется по кругу. Исключение — terminal-валидация явно требует
недостающий второй search или открытую typed-карточку: при оставшемся бюджете
она возвращает агента к evidence tools, сбрасывает bounded schema-repair и
показывает ошибку в compact working memory. Код не выбирает новый scope или
запрос, он только не даёт сериализации скрыть незавершённое доказательство.

Подтверждённый моделью scope, для которого ещё нет фактической записи
`search_norms_batch` в query trace, входит в
`must_search_selected_scopes`. Пока список не пуст, следующий ход для этого
scope — scoped batch search; каталожный переход не считается поиском нормы.

Если повтор произошёл до первого scoped search/read, terminal-решение ещё
нельзя обосновать. В этом случае активная разговорная история очищается до
неизменяемого task prefix, а Qwen получает компактный working memory с
последними catalog steps и точным `next_action`; полный старый tool trajectory
остаётся только в checkpoint/event audit. Новый model-authored
`catalog_query` разрешает повторно построить shortlist того же семейства после
неудачной первой гипотезы о сборнике.

Transport timeout structured mapping не считается schema-validation attempt:
checkpoint сохраняет blocker, но повторный запуск может снова сериализовать
те же model-owned решения. Точные строковые значения `true`/`false`, которые
локальная модель иногда возвращает для schema-boolean, нормализуются только в
объявленных boolean-полях tool contract; профессиональные значения и строки
не переписываются.

Однострочная terminal-сериализация использует decision-specific JSON-варианты:
`bind` получает полный technology/candidate contract, а `covered_by` и
`unbound` не повторяют bind-only поля. Для `unbound` Qwen передаёт только своё
решение, краткие причины отклонения и coverage-вывод; выполненные запросы и
коды открытых карточек присоединяются из typed tool trace. Terminal `unbound`
отклоняется, если сам требует продолжить поиск либо ссылается на норму/сборник
без открытой через `read_norms_batch` карточки. При усилении validation contract
старое невалидное checkpoint-решение остаётся в tool trajectory, но возвращается
в pending вместо молчаливого продолжения расчёта.

В строгом РИМ-контуре schema показывает `bind` только для уже открытых
typed-карточек, чей измеритель формально совместим с единицей исходной строки.
Это не выбор нормы кодом: Qwen по-прежнему решает `bind|covered_by|unbound`,
но не может сериализовать шифр из другого измерителя. `exact` также
отклоняется как внутренне противоречивый, если та же модель указала
`missing_operations`, unresolved condition либо limited conclusion. Такие
self-conflicts сохраняются в mapping revision и блокируют lock до явного
профессионального решения.

После успешного mapping checkpoint очищается, но история инструментов не
исчезает: mapping revision сохраняет SHA-защищённый `agent_audit` с версией
validation contract, catalog/query trace, typed tool trajectory, lifetime
budget и временем. Этот audit не подаётся Qwen обратно целиком.

Идентичность проектного источника не принадлежит модели. При уточнении
черновика она может изменить формулировку работы и объяснение количества, но
`source_ref`, `source_refs` и `source_row` существующего `work_id` наследуются
из родительской VOR-ревизии. Новая производная работа допустима, только если
она ссылается на уже известные project source refs родителя. Нормативный источник хранится отдельно в mapping как
`norm_source_ref` и не может подменить строку исходного XLSX.

Mapping lock и final lock — разные пользовательские ревизии. Закрытие
requirement не обновляет старую расчётную трассу и не разрешает финализацию:
новый `priced_draft` появляется только после повторного детерминированного
расчёта.

Ни одна строка источника не обрезается transport-лимитом. Specification intake
обрабатывается моделью пакетами по пять строк и после каждого пакета сохраняет
`vor_draft` checkpoint; norm mapping получает все строки ВОР. Глобальная
проверка строит connected conflict groups и повторно вызывает модель только для
них, сохраняя остальные решения дословно. Итоговая revision требует ровно одно
терминальное `bind|covered_by|unbound` для каждого `work_id`. `unbound` остаётся
видимой строкой с пустыми денежными полями,
причиной и provenance и не блокирует расчёт остальных строк.

Расчёт разрешён для `mapping_globally_reviewed` и создаёт только
`priced_draft`; финал по-прежнему требует пользовательский `mapping_locked`.
`POST /api/rim/sessions/{id}/recalculate` без `scenario_id` строит canonical
projection уже проверенных решений, не выбирая норм кодом. Resolved КАЦ и
коэффициенты читаются из durable requirements при следующем пересчёте.

## Строгий нормативный контракт

Для диалоговой РИМ-сессии разрешена только цепочка:

```text
browse_norm_catalog(root)
  → continue_norm_catalog | ask_norm_catalog_fact | broaden_norm_catalog | unbound_norm_catalog
  → family → collection → section → table
  → search_norms_batch
  → read_norms_batch
  → submit_lsr_mapping
```

Корневое меню пяти семейств код сразу помещает в working memory; отдельный
LLM-вызов `browse root`, результат которого заранее известен оркестратору, не
выполняется. Первый содержательный ход Qwen — выбор семейства по model-visible
паспортам из
`config/domain/smeta_normative_catalog.json`: официальное назначение, типовую
область, исключения, вопросы, нормативный акт и навигационный источник. Затем
модель typed-переходом фиксирует точный `selected_node_id`, evidence и
`confidence`. Полный перечень сборников модели не передаётся: её
краткий сметный `catalog_query` с системой, предметом и операцией запускает
ограниченный поиск норм только в выбранном семействе. Варианты словаря
маршрутизации имеют явные стадии: признаки норм не загрязняют выбор сборника.
Shortlist не более чем из шести сборников сначала сохраняет верх официального
лексического каталога, затем дополняется общим rerank без дублей. Поэтому
общий семантический rerank не может целиком вытеснить из видимого меню прямой
официальный каталоговый матч; код при этом не выбирает сборник за Qwen.
Трасса фиксирует lexical rank, rerank rank и метод fusion. Rerank обязателен
даже для SQLite-only результата; ошибка reranker останавливает выбор сборника.

Каждый каталоговый элемент имеет `node_id`, `parent_id`, `node_type`, `cipher`,
официальное название/описание, `source_ref` и редакцию. Код разрешает только
переход к реально показанному ребёнку. Evidence может ссылаться только на
показанный узел и существующее поле; выбранный узел не может одновременно
находиться в `rejected_nodes`. `broaden_norm_catalog` возвращает ровно к
родителю. Применимость при этом остаётся решением Qwen, а не функцией каталога.

`search_norms_batch` принимает только `scope_mode=scoped`; глобальный либо
неполный scope отклоняется до retrieval. `SmetaNormToolSession` проверяет
двухступенчатую трассу выбора. Если передан `table`, его префикс и фактическое
наличие проверяются внутри той же пары `base_type + collection`; таблица из
другой книги или сборника не попадает в retrieval. Только после этих проверок
фильтры передаются в `browse_norms_many()` — SQLite FTS/Qdrant RRF/rerank.
Старый текстовый `estimate_harness_service.search_norm()` не является точкой
входа этого модуля.

Каждый `work_id` проходит собственный typed-маршрут. `search_norms_batch` не
копирует подтверждённую ветвь из другой строки и не может создать scope:
семейство, сборник, раздел и таблица должны уже находиться в checkpoint этой
строки.

Каждый принятый или отклонённый переход получает `trace_id` и `outcome`.
Успешный trace содержит текущий и выбранный узлы, evidence вместе с фактическим
значением поля и `source_ref`, отвергнутые альтернативы, confidence,
missing facts и следующий уровень. До mapping он хранится в durable checkpoint,
после mapping — в SHA-защищённом `agent_audit`; отклонённая попытка не затирает
последний успех.

`GET /mapping/progress` проецирует этот журнал в читаемый активный маршрут,
счётчики принятых/отклонённых переходов и фактический `model_wait_ms` каждого
хода. В UI маршрут и ошибка последнего отклонённого перехода видны без чтения
сырого JSON checkpoint.

Тот же конфиг хранит пользовательский реестр источников РИМ с SHA исходной
`нормативка_под_РИМ.xlsx`: коэффициенты, Сплит-форму, ФСЭМ, КАЦ, НР и СП.
`rim_knowledge_service.py` передаёт Qwen только релевантные текущему этапу
карточки. Это навигация к `rules_store`/`price_store`/`fsem_store`/`kac_store`,
а не значения для расчёта; точные цифры по-прежнему читаются typed-сервисами.

Shortlist из RAG имеет роль навигации. Он может дать Qwen `norm_key`,
technology hints и `questions_to_ask`, но не является расчётным evidence.
Выбранная строка проходит только после `read_norms_batch`: mapping хранит
`card_opened=true`, `norm_source_ref`, редакцию и identity целиком прочитанной
карточки versioned structured store. Норма без открытой карточки блокирует
mapping lock и расчёт.

`questions_to_ask` из навигационной карточки передаются Qwen отдельным
ограниченным ходом. Модель выбирает один наиболее ценный вопрос, формулирует
его по-русски и сохраняет как открытый вопрос сессии. В UI варианты ответа
показаны кликабельными кнопками; свободный текст тоже допустим. Короткий
следующий ответ интерпретируется относительно этого вопроса, а не запускает
новый workflow.

Для локальной Qwen 3.5 9B преобразование спецификации идёт последовательными
bounded transport-пакетами по 5 исходных позиций. В каждом пакете доступен
только `draft_work_schedule`, а checkpoint хранит принятые model-owned строки
и следующий offset. Вопрос разрешается после сохранения полного source-linked
черновика. Это ограничение контекста, а не автоматический выбор работ кодом.

MLX Host сохраняет bounded KV/prefix cache для побайтово стабильного начала:
общий `system`, неизменяемые схемы четырёх route-tools и исходный mapping packet.
Фаза не меняет system и передаётся последним компактным working-memory
snapshot. После tool call оркестратор строит новый snapshot и не возвращает
старую tool-пару в prompt. Поэтому следующий уровень повторно использует
стабильный префикс, тогда как allocator cache по-прежнему очищается после
хода, а веса остаются тёплыми до TTL. В OpenAI-совместимом ответе reuse виден
как `usage.prompt_tokens_details.cached_tokens`.

Каждый вызов пишет покадровый профиль: `phase`, `prompt_tokens`,
`cached_prompt_tokens`, `uncached_prompt_tokens`, `completion_tokens`, TTFT,
prefill/decode/tool/total time, число видимых детей и размер working memory.
Это позволяет отдельно отличить холодный префикс от лишних LLM-ходов. На
реальном Mac Qwen 3.5 9B переход `family → collection` повторно использовал
`3024/5205` prompt tokens (58,10%); холодный выбор семейства занял 82,36 с,
следующий кешированный выбор сборника — 62,96 с. Это профиль разработки, а не
production SLA.

## Расчёт и сценарии

Код не строит Cartesian product профессиональных альтернатив. Он показывает
теоретическое число комбинаций и считает только совместимый сценарий,
составленный моделью или пользователем. Лимит по умолчанию — 1000; превышение
возвращается как blocking issue.

Сценарий преобразуется в canonical visible rows и передаётся
`smeta_core.application.calculate_visible_rows_revision`. Пропущенная цена
читается из exact resource trace и создаёт blocking `kac`, а не нулевую цену.
Имеющийся РИМ renderer строит графы 1–12; дополнительными листами идут
`Недостающие данные` и `Аудит`.

## API и UI

Роутер `proxy/routers/rim.py` предоставляет owner-scoped `/api/rim/sessions/*`:
сессии и ревизии, импорт/ВОР, model tools и agent turn, mapping/XLSX/global
review/lock, read-only `/mapping/progress`, сценарии и расчёт
(`/combinations/calculate` или `/recalculate`), requirements, final lock,
export и audit.

Отдельной NiceGUI-вкладки «Сметный проект» в production shell нет. Пользователь
работает через универсального агента; owner-scoped session API и компактная
`/mapping/progress`-проекция остаются инструментальным контрактом для агента и
будущих интерфейсов. Источники в API сохраняют проектное имя файла, лист и
строку, а для норм — редакцию ФСНБ, шифр и raw ref.

`GET /api/rim/sessions/{id}` возвращает read-only `next_step` из
`rim_next_step_service.py`: один фактический следующий этап, понятную подпись,
state-scoped prompt и целевую рабочую вкладку. Поэтому отсутствие открытого
вопроса больше не называется готовностью всей сметы. Пустой composer не
отправляет фиктивное сообщение: явная кнопка запускает только разрешённый для
текущего состояния agent turn.

Если вопрос был открыт уже после сохранения mapping, ответ пользователя не
оставляет сессию в тупике `mapping_selected|candidates_ready`. Оркестратор
восстанавливает model-owned решения и typed evidence из текущей immutable
mapping revision, передаёт подтверждённый ответ в mandatory same-model global
review и строит canonical денежный draft. Поиск всех строк заново не
запускается; структурные blockers по-прежнему останавливают расчёт и остаются
видимыми. Команда «Сделай ЛСР» использует ту же ветку. Сметное ядро, формулы и
выбранные моделью нормы этим UI/application-layer продолжением не изменяются.

## Проверки кандидата

- unit/API/XLSX/state/UI тесты находятся в `tests/test_rim_*.py` и
  `tests/test_sovushka_uikit.py`;
- isolated Mac browser smoke проверен на desktop и 390 px без горизонтального
  переполнения;
- реальная `СКС.xlsx` распознана как спецификация: 70 позиций, 3 раздела,
  structural issues отсутствуют; после ужесточения draft-schema Qwen сохранил
  первые 5 строк с обязательными `work_name`, `unit`, `quantity`,
  `quantity_origin`, `source_ref` и задал технический вопрос «монтаж и
  подключение входят в ВОР или только поставка?» с двумя вариантами ответа;
- реальный Mac Qwen 3.5 9B первым вызовом выбрал `browse_norm_catalog`, не
  придумав шифр;
- реальный isolated Mac cache-probe на Qwen 3.5 9B повторно использовал
  `14 968` из `14 996` prompt tokens; второй ход занял `2,24 с` после
  холодного первого хода `139,17 с`;
- после разделения фаз Mac Qwen 3.5 9B на первой строке реальной `СКС.xlsx`
  валидно выбрала `catalog:family:ГЭСНм` за `68,62 с`: feature card распознал
  разобранный напольный шкаф как объект монтажа, evidence сослался на реальные
  `purpose/typical_scope/not_for`, четыре соседних семейства были отвергнуты;

### Автономизация и устойчивость каталога (версия 0.27.28)

1. **Авто-подстановка `catalog_query`**: если локальная модель опустила `catalog_query` в `continue_norm_catalog`, код выводит 2–12 поисковых слов из `work_features.operation / equipment / system`.
2. **Fallback `work_features` на уровнях `section`/`table`**: при переходе к разделу или таблице, если модель не продублировала `work_features`, код берет сохраненную карточку `work_features` из принятого семейства `self.selected_base_types[work_id]`.
3. **Fallback `work_id` при однострочном пакете**: если `len(self.by_id) == 1` и модель не передала `work_id` в `item` вызова инструмента, код автоматически подставляет единственный `work_id`.
4. **Валидация `evidence` для `current_node_id`**: разрешено использовать `source_node_id == current_node_id` (родительский узел), позволяя модели цитировать назначение сборника/семейства при выборе раздела.
5. **Soft-stop `catalog_stall`**: 3 подряд одинаковых отказа `reject` фиксируют `catalog_stall` и останавливают бесконечный цикл ходов.
