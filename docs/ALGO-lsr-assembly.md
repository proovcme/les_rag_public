## P9.16 — структурная ошибка material_review_status (.200 source)

ACTIVE Markdown decoder проверяет явно непустой material_review_status по уже
документированным confirmed/not_present/unresolved/rejected. Регистр не меняется:
calculator и раньше сравнивал confirmed буквально. Пустые/absence markers допустимы.
Ошибочное поле даёт invalid_decision_field → model_row_format_error, сохраняет
source anchor, исходные cells/header/строку и SHA. SHA строки исключает line terminator;
пробелы исходной строки сохраняются. Diagnostic показывает недопустимые поля/значения,
фактическую и ожидаемую ширину и число trailing padding, но не место пропуска.

Одна лишь короткая строка не доказывает сдвиг: existing trailing optional padding
сохранён. Не производится вставка ячейки в середине, перенос статуса, изменение
нормы/ресурса/коэффициента/цены. Ошибочная строка остаётся открытой; соседи могут быть
упакованы обычным путём. Cursor/reopen и _previous_rejections возвращают точную
field-grammar причину и исходную разметку следующему штатному model turn, без нового
автоматического цикла. Raw choices доступны для проверки, ошибочные поля не считаются
подтверждённым структурированным решением. Canonical/live candidate pending.

## Восстановление после отмены и сбоя хранения (P8, кандидат 0.30.183)

После завершённого ответа модельные строки связываются с доставленными источниками;
запись принятого прохода выполняется в `finally` вокруг доставки и упаковки.
Если await доставки либо расчёта отменён, отмена доходит до вызывающего кода,
а cursor сохраняет решения, evidence и прежнее документное ценовое основание.
Повтор собирает книгу из сохранённой ревизии до нового обращения к модели.
Частичный поток токенов не выдаётся за завершённое решение.

Разрыв между сохранением immutable artifact и завершением workflow checkpoint
восстанавливается по точному `decision_checkpoint_id`. Должен существовать один
артефакт с теми же source scope, моделью, profile/preset, решением и tool identity;
новые записи дополнительно несут session/attachment SHA/normalized args SHA.
Прежние записи без этих дополнительных полей совместимы; их значения не выдумываются.
Несколько ревизий либо конфликт provenance дают явную ошибку, а не новый расчёт.
SHA и наличие XLSX проверяются до возврата; повреждённый файл сохраняется в истории,
а один детерминированный repair checkpoint восстанавливает дочернюю ревизию.
Повторный отказ checkpoint storage не запускает adapter ещё раз.

У нестримингового `/chat` отмена ждёт завершения SQLite begin/complete/release worker.
Освобождается только собственный started claim; чужой in-progress не снимается.
Ошибка cleanup сохраняется причиной исходной отмены. При ошибке записи готового
ответа остаётся прежняя явная политика in-progress; TTL/lease schema не изменены.

Границы: проверены контролируемая отмена/исключения и последовательный retry с
переоткрытием хранилищ. `finally` не является журналом hard kill процесса; конкурентный
exactly-once нескольких клиентов не заявляется. Installed user journey проверяется в P9.
Существующий guard пустой конвертации уже срабатывает до удаления старых dense/sparse
points и lexical rows; P8 добавляет доказательство, не второй индексный механизм.

Сохранённый отказ IQ3 от07.10 содержит `Vulkan ErrorOutOfDeviceMemory` в backend,
а не доказанный слишком короткий timeout. Transient batch256/ubatch64 позволил
загрузить ту же35B при32768; это не доказало финальную смету. Timeout, модель,
карточки и context budget в P8 не меняются; живые границы отделены от offline tests.


## Явная область и заголовок нормы (P7, кандидат 0.30.182)

Общий пользовательский scope (`dataset_ids`) не является scope выделенной
нормативной библиотеки или отдельного каталога практики. Primary trace явно
разделяет эти источники и не утверждает, что UUID-фильтр применён к нормативам.
Связь UUID нормативного dataset с dedicated generation пока не подтверждена;
она не вычисляется по имени. Это видимая граница текущего контракта, а не
реализованное переключение между произвольными нормативными базами.

Лексический поиск сохраняет прежний порядок exact AND → prefix AND → prefix OR.
Trace записывает фактически исполненные условия, количество кандидатов каждого
шага и ограничение первых12слов. Ослабление до OR больше не скрыто за одним
исходным текстом запроса. Профессиональные дополнительные запросы код не строит.

Явно переданные family/collection ограничения пересекаются с точным шифром,
таблицей, typed search и native dense+sparse RRF до top-k. Пустое пересечение
не означает отсутствие фильтра. Исходный запрос сохраняется; код не определяет
сборник по профессиональным словам. В существующем индексном payload нет поля
collection: принадлежность задаётся точными norm_key из нормативного SQLite,
проверяется ревизия, перестройка индекса не нужна. Trace показывает область и
способ её применения. Это исправление уже переданного scope; оно не добавляет
в чат обязательный этап выбора сборников.

Буквальный заголовок таблицы из source hierarchy передаётся рядом с названием
варианта в preview/full-card и в rerank input. При отсутствии заголовка текст
не сочиняется. Состав операций сохраняется; бюджет и полнота проверяются
отдельно от пригодности профессионального решения.

Reranker получает весь pool и возвращает полный порядок до окончательного
top-k. Native RRF и фактический rerank объединяются как два сигнала. Неполный
ответ отмечается `partial_response`: отсутствующие ранги не дополняются старым
порядком как будто это второй голос. Исходный native RRF остаётся целиком;
при транспортном отказе используется его порядок с явным fallback status.
В режиме официального каталога без fusion недостающий хвост сохраняется как
fallback по шифру, также с отметкой неполного ответа.

Офлайн-тесты не доказывают качество поиска. Сопоставимые запросы и same-pool
rerank, действующие настройки/маршрут, installed acceptance фиксируются в
аудите P7/P9. Installed .171/build811 пока неизменен.

## Ценовое основание документа (кандидат 0.30.180, P5)

Для новой ведомости cursor SQLite атомарно сохраняет `document_price_basis`
по session/source_revision перед поиском цен и упаковкой. Книга определяется
настоящим SHA256, идентификатором, регионом, периодом и доступной исходной версией;
неизвестная версия остаётся None. Глобальный default выбирает основание нового
документа, но не меняет продолжение прежнего. Исторический документ без pin
получает `legacy_unpinned`, а не выдуманное старое основание.
Если таблица не дала распознанных строк, identity берётся из проверенного SHA
исходного вложения; для текста без файла — из всего текста. Разные документы
не делят identity пустого списка. Неизвестный период цены в шапке XLSX указан
как «Не указан», а не восстановлен из имени файла справочника.

Обычный и native model research используют локальный callback закреплённой книги.
Workbook context передаёт то же основание и SHA вложения; запрос другой исходной
книги с чужим context отклоняется до упаковки. SHA выбирает trusted reader,
не модель. Явная смена основания через trusted document contract меняет evidence,
checkpoint/artifact identity и calculation_ref даже при тех же суммах.
Ранний общий semantic answer cache для primary estimate с вложением обходится
до закрепления основания (lookup и store); lexical caches и точные artifacts
сохраняются. Причина отражена в trace, нового скрытого runtime-фактора нет.

Reader цены проверяет согласованную ревизию файла. Закреплённый snapshot может
продолжить расчёт A в памяти; после его утраты подменённый файл даёт явный
`price_basis_conflict`, без перехода на B. Lookup не возвращает первый из разных
exact records одного кода: неоднозначность остаётся неизвестной ценой. Карточка,
чек и XLSX сохраняют book/record provenance; несовместимая единица не умножается
на количество. Цена за1000м приводится к метру один раз, с сохранением точных
операндов и формул книги.

При новом чтении содержимое проверяется настоящим SHA, а не только размером и
временем файла: воспроизведено совпадение метаданных после быстрой перезаписи.
Повторный расчёт по сохранённому неизменному snapshot не перечитывает файл для
каждого ресурса. Та же проверка усиливает P2: новая нормативная SQLite-ревизия
не может получить прежний SHA из metadata-only cache. Стоимость свежего чтения
базы учитывается отдельно; офлайн корректность не доказывает скорость live-пути.

В primary document calculation цена из нормативного SQL — `normative_price`,
а не ручная текущая цена. Расчёт использует закреплённый текущий справочник;
нет цены — пустые J/L, частичный итог и причина. Явно снятый ресурс имеет
нулевое влияние даже при неизвестной цене: J остаётся пустой, L=0.
Прежний прямой manual API сохраняет явную ручную цену. Это отделение
ценового происхождения от выбранного моделью ресурса; нормы/состав не заменяются.

## Точный адрес ресурса (кандидат 0.30.179, P4)

Опциональный `target_resource_id=row:<SQL id>` выбирает исходную строку в
нормативной ревизии родительской работы `included_in`. Адрес не является
позицией после сортировки. `target_resource_code`, если указан, проверяется
на совпадение; неверный ID не запускает подбор другого ресурса по коду.
Ресурс без кода допускается по точному адресу. Старый code-only путь остаётся
для однозначного одиночного ресурса.

Reader сохраняет `source_resource_ids`, включая SQL ID0. Прежняя дедупликация
по виду/коду либо имени/единице/расходу/цене не меняет арифметику. Если она
объединила строки, все исходные ID остаются в группе `group:<SHA>`, связанной
с нормативной ревизией. Выбор одного члена такой группы даёт
`resource_group_scope_required`; действие по группе требует явного выбора
моделью адреса всей группы, её декларации и всех членов в доставленной карточке.

`resource_delivery_proofs` проверяет SHA и точные spans в непрерывном префиксе
карточки **фактических final/fallback messages**. Цитата в вопросе после
обрезанной карточки не восстанавливает её доставку. Доказательства сохраняются
в trusted snapshot родительской операции; переданные моделью proof/identity
поля отбрасываются. После перезапуска cursor SQLite восстанавливает доказательство
того же родителя и той же ревизии. Старый snapshot без proof остаётся неизвестным.
Packet SHA не меняет профессиональную ревизию решения.

Материальное распределение и снятие используют ключ работа+ревизия+точный ресурс.
Одинаковый код у разных исходных строк не смешивает счётчики. Снятие изменяет
только названную строку; повторное снятие даёт конфликт. Явная замена по прежнему
контракту — снятие плюс отдельная поставка `replaced_by`. Чек и XLSX сохраняют
исходные ID, исключённый расход (включая неизвестный), новое количество и стоимость.
Для снятой машины исходное количество учитывает именно машинный коэффициент;
ФСЭМ убирает только её часы экипажа. Производные экипажи не получают SQL ID.

Это исполнение выбранного действия, а не проверка профессиональной пригодности.
Прямые синтетические тесты используют явно обозначенные fixture-цены; это не
цены текущего справочника и не live-приёмка сметы. Ценовое происхождение — P5.

## Исходные ячейки и охват (кандидат 0.30.178)

Транспорт XLSX/CSV сохраняет позиции пустых ячеек и настоящий числовой0.
Пустой хвост строки без значений не раздувает контекст из-за форматирования
Excel. При разборе он дополняется до ширины содержательной шапки; внутренние
пустые ячейки и любые реальные данные в дальних столбцах сохраняют координаты.
Версия текстового транспорта `les.tabular.cells.v2` обратимо экранирует
разделитель `|` и обратную косую черту внутри ячейки; прежний текст без маркера
читается по прежним правилам. Начало нового файла сбрасывает карту столбцов.
Разреженная PDF-таблица не сжимает каждую строку независимо: допустима только
общая очистка полностью пустых столбцов. Поэтому количество, масса и артикул
не меняют принадлежность столбцу из-за пустой соседней ячейки.

`vor_rows` читает полную строку по шапке: пустое количество остаётся None,
масса справа не становится объёмом. Совместимость с прежним сжатым транспортом
ограничена неполной шириной и признаками сдвига; это не основание подменить
явно указанную единицу или неизвестное количество полной строки.
Нумерованная строка без unit/quantity остаётся в исходном охвате, если нет
явного структурного признака раздела. Слово «всего» внутри работы не удаляет её.
Реестр источника и порция учитывают такие строки; частичный ответ модели
оставляет непоказанные/неразрешённые строки открытыми в листе «Исходные строки».

Исправление сохранённых cells/raw может изменить `source_revision` старого
повреждённого транспорта. Старые решения не переносятся в новую ревизию
автоматически и не объявляются подтверждёнными. Полный исходный файл остаётся
основанием нового чтения; профессиональные решения код не восстанавливает.
Этот reader по-прежнему требует распознаваемой шапки и номера позиции;
поддержка произвольных таблиц без номера этим изменением не заявляется.

## Версия показанной нормы → расчёт (кандидат 0.30.177)

После ответа модели `bind_normative_identity` механически связывает каждую
операцию с metadata фактически доставленной карточки. Модельные поля identity
и evidence_snapshot не принимаются на доверие. Новый локальный Qref не наследует
старую карточку, даже если текущую исключил Governor; rebuild использует только
сохранённое доказательство той же строки/операции/нормы. После cloud fallback
доставка проверяется по фактически отправленному fallback prompt.

`positions_from_visible_lsr_rows` передаёт expected_identity в reader и сохраняет
приватный снимок прочитанной нормы на один расчёт. Материальные действия и trace
не подчитывают новую версию посреди операции. JSON модели не может создать этот
внутренний тип. Explicit resources также не обходят проверку нормативной версии.
При conflict исходный выбор сохраняется в binding, стоимость другой версии не
считается. Пустой расчёт с таким конфликтом имеет `norm_revision_conflict`, а не
ложное отсутствие выбора нормы. Legacy primary-решение без provenance остаётся
`unpinned`: известная арифметика доступна, полная сумма и final не заявляются.

Identity участвует в `decisions_revision` и `calculation_ref`; старое подтверждение
не принимает новую нормативную ревизию даже при той же сумме. В XLSX SHA
рассчитанной нормы сохранён в комментарии, expected/actual конфликт — на листе
«Проверка». Неизменные профессиональные решения остаются ответственностью модели.

## Неизвестное количество и стоимость (кандидат 0.30.176)

В `rim_lsr_trace_service` неизвестный нормативный расход сохраняется как
неизвестные количество и стоимость ресурса. В trace/расчётном чеке эти значения
не превращаются в 0; строка получает `quantity_missing`, а `full_amount` остаётся
неизвестной. `known_amount` суммирует только независимо рассчитанные значения.
Настоящий расход 0 сохраняет смысл нуля. Нечисловая/не конечная явная цена также
не считается нулевой ценой.

ФСЭМ не подтверждает равенство агрегированных и разложенных часов, если
исходные часы машин/машинистов неизвестны; исходные ресурсы сохраняются с
неразрешённым статусом. Трудовые итоги при неизвестной составляющей не выдаются
за известный ноль. XLSX оставляет неизвестные значения пустыми и не создаёт
формулу стоимости с пустым количеством. Смысл нормы и модельные решения не
изменяются. Проверка: `tests/test_smeta_unknown_consumption_contract.py`.

При модельном снятии ресурса действующий вклад может стать нулевым, но исходное
`excluded_quantity` сохраняет неизвестность. Лист «Проверка» отличает неизвестное
снятое количество от настоящего 0. Неизвестный доступный остаток не признаётся
нулевым запасом и не подтверждает покрытие: binding получает
`resource_quantity_unknown`, сохраняя исходное решение модели.

Связывает кирпичи сметного ценообразования в сборку **позиция-к-позиции**. 0 LLM (ADR-11).
Финальная веха ценообразования: всё построенное сходится в один конвейер.

## Конвейер

```
объём (ВОР) → ресурсы позиции → цены (ФГИС ЦС lookup / КАЦ) →
  ОЗП / ЭМ(машины+ОТм) / М → коэф. стеснённости → НР / СП → Всего по позиции → свод в ЛСР
```

## Бухгалтерия позиции (выверена на Эталон_кровля, поз.1)

| Величина | Формула | Эталон |
|---|---|---|
| ОЗП | Σ labor | 3750.23 |
| ЗПМ | Σ machinist (ОТм) | 458.68 |
| ЭМ | машины + ЗПМ | 992.40 |
| М | Σ material | 83.62 |
| Прямые | ОЗП + ЭМ + М | 4826.25 |
| ФОТ | ОЗП + ЗПМ | 4208.91 |
| НР | ФОТ × нр% (109) | 4587.71 |
| СП | ФОТ × сп% (57) | 2399.08 |
| **Всего** | Прямые + НР + СП | **11813.04** |

## Шаги

1. **Ресурсы → цены** (`compute_position`): для каждой строки ресурса цена = явная `price`, иначе
   `code`→ФГИС ЦС (`fgis_price_service.lookup`), иначе material→КАЦ по наименованию; нет цены → флаг.
   Стоимость = qty × price.
2. **Агрегация по видам** (`kind`): labor→ОЗП, machinist→ЗПМ, machine→машины, material→М; ЭМ=машины+ЗПМ.
3. **Стеснённость + НР/СП** (делегирует `stesnennost_service.apply_position`): при k≠1 берётся
   скорректированное «Всего», иначе базовое. См. [[ALGO-stesnennost]].
4. **Свод** (`assemble`): по разделам + итог ЛСР (base_total / total / stesnennost_uplift) + флаги
   позиций без цены (кандидаты на КАЦ).

## РИМ-трасса граф 2-12

`rim_lsr_trace_service.build_position_trace` — отдельный evidence-слой для Приложения 4 к Методике
421/пр (форма ЛСР). Он не заменяет `lsr_assembly_service`, а раскладывает одну позицию в проверяемые
строки: работа, коэффициент, ОТ(ЗТ), машины, ОТм(ЗТм), материалы, прямые, ФОТ, НР, СП, итог. Для ФГИС
ЦС сохраняет происхождение цены: текущая цена (графа 10) или базовая цена × индекс (графы 8-10).

`build_lsr_trace(positions)` — **многопозиционная** трасса: каждая позиция через тот же
`build_position_trace` (числа те же — gold сохраняется), группировка по разделам (поле `section`,
порядок первого появления), свод = Σ позиций (прямые/ФОТ/НР/СП/Всего + нормативные чел.-ч рабочих/
машинистов для шапки). Рендер — `rim_trace_xlsx_service` (форма Приложения 4): одна позиция —
`render_trace_xlsx`; смета — `render_lsr_xlsx` (шапка с общим итогом + разделы с заголовком и «Итого
по разделу N» + «ВСЕГО по смете»). Числа не пересчитываются (рендер ГОТОВОЙ трассы, 0 LLM).

`build_lsr_trace_from_visible_rows(rows)` — мост из уже выбранных/видимых строк ЛСР/ВОР в трассу.
Он не ищет и не выбирает норму: строка должна содержать `basis`/`code` с шифром. Код только
нормализует шифр, переводит физическое количество в измеритель нормы (`61 м2` при норме `100 м2`
→ `0.61`), раскрывает ресурсы, ищет цены и возвращает `row_bindings`. Строки без шифра, без
количества или с конфликтом единиц не попадают в финальный расчёт и блокируют `priced_final`.

Если `book` не передан, все LSR/API пути используют единый `fgis_price_service.resolve_pricebook_path()`:
`LES_DEFAULT_PRICEBOOK` → `spb_2kv2026`/`sankt-peterburg_2kv2026` → доступные книги 2026 → первая
обычная книга. Scratch-файлы (`*_refresh`, например `spb_refresh`) не становятся дефолтом и не
показываются как обычные книги; их можно использовать только явным именем для диагностики/добора.

## Индекс ГЭСН/ГЭСНм

Ключ нормы в parquet — не голый номер `38-01-001-01`, а `norm_key = <base_type>:<код>`, например
`ГЭСН:38-01-001-01` и `ГЭСНм:38-01-001-01`. Это обязательный invariant: строительные, монтажные,
пусконаладочные и ремонтные сборники могут иметь одинаковые номера таблиц, но разные ресурсы.

Для FGIS SearchEstimatedRates возможны несколько опубликованных версий одной таблицы. Парсер берёт
актуальную версию по максимальному `id` внутри одинаковых `(documentTypeName, documentName)`, иначе
одна норма получает дубли ресурсов из старой и новой публикации.

Тарифные коды труда вида `1-100-40` сохраняются как `resource_code` и ценятся по Сплит-форме ФГИС ЦС.
Агрегированная строка `Затраты труда машинистов` без разряда/кода раскладывается только если машины
позиции полностью покрываются явным маппингом машина→машинист, а сумма машино-часов совпадает с
агрегатом ОТм. Если покрытие неполное — строка остаётся `missing`, без молчаливой подстановки.

Текущий минимальный маппинг нужен для проверенного кейса столпа: `91.05.05-015` → `4-100-060`
(машинист 6,0), `91.14.02-001/002` → `4-100-040` (машинист 4,0). Расширять его нужно только по
ФСЭМ/официальному источнику, а не по догадке модели.

## Где в коде

- Сервис: `proxy/services/lsr_assembly_service.py` (переиспользует `stesnennost`/`fgis_price`/`kac`).
- РИМ-трасса: `proxy/services/rim_lsr_trace_service.py` (`build_position_trace` — позиция, графы 2-12;
  `build_lsr_trace` — смета: разделы + итоги разделов + общий свод;
  `build_lsr_trace_from_visible_rows` — выбранные строки ЛСР/ВОР → `priced_partial` trace).
- Рендер формы ЛСР РИМ Приложения №3: `proxy/services/rim_trace_xlsx_service.py` (`render_trace_xlsx` — позиция;
  `render_lsr_xlsx` — многопозиционная смета).
- API: `POST /api/lsr/assemble`; `POST /api/lsr/rim-trace[/export]` (позиция);
  `POST /api/lsr/lsr-trace[/export]` (смета → XLSX-форма);
  `POST /api/lsr/lsr-trace/from-rows[/export]` (видимые строки с выбранными шифрами → trace)
  (`proxy/routers/lsr.py`).
- GUI: «Инструменты» → карточка «Сборка ЛСР» (позиции JSON + книга/условие → свод по разделам).
- MCP: `les_lsr_assemble`.
- Тесты: `tests/test_lsr_assembly_service.py`, `tests/test_rim_lsr_trace_service.py`,
  `tests/test_rim_trace_xlsx.py` — **gold: позиция эталона = 11813.04; смета 2× = 23626.08**.

## Граница (что осталось)

- Рендер в форму Приложения 4 (одна позиция + многопозиционная смета: разделы + итоги разделов +
  «ВСЕГО по смете») — **готов**. Осталась полная GRAND-фиделити (179 кол., НР/СП с типом работ в
  графах), реальные метаданные шапки и вызов формы прямо из чата (сейчас — через API-эндпоинт).
- ФСЭМ-связка «машина → машинист» пока частичная; для новых машин без маппинга ЛСР честно вернёт
  `needs_price`, пока не загружен официальный справочник.
