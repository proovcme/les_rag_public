# Аудит нормоконтроля и план стабилизации

Дата среза: 2026-07-23  
Базовая ветка: `audit/smeta-stabilization`, commit `0849caf`  
Основной rulepack: `ГОСТ Р 21.101-2026`

## Вердикт

Нормоконтроль — самый собранный из четырёх аудируемых контуров на уровне
offline-кода: текущий профиль даёт `55 passed`. Есть review map, формальные
проверки, retrieval evidence, human decision workflow и JSON/HTML/XLSX
экспорт. После полного public sync добавлен профессиональный skill contract,
который явно разделяет решение модели и вычислимые проверки.

При этом это ещё не stable нормоконтроль полного комплекта. Rulepack содержит
15 целей и покрывает базовые шифры, ведомость, формат листа, штамп, стадию и
готовность PDF. Часть layout-проверок остаётся `manual_required`, retrieval
в sync-пути лексический, а нормативный источник ГОСТ не может публиковаться
целиком без подтверждённого права. Живой end-to-end прогон на публичном
обезличенном комплекте отсутствует.

Статус — **устойчивый offline review kernel, pre-stable product workflow**.

## Что уже работает

- Review map `gost_r_21_101_2026` с 15 типизированными целями.
- Computed checks:
  - версия rulepack;
  - согласованность базового шифра;
  - ведомость против фактического состава;
  - формат обозначений и разделителей;
  - геометрия формата PDF-листа;
  - наличие основной надписи;
  - техническая готовность PDF.
- Retrieval checks:
  - устаревший ГОСТ Р 21.101-2020 в корпусе;
  - стадия ПД/РД;
  - поиск requirement source в нормативном dataset.
- Честные статусы `computed_issue`, `supported_by_evidence`,
  `manual_required`, `review_needed`, `not_applicable`.
- Решение инженера хранится отдельно: `confirmed`, `rejected`,
  `needs_more_evidence`.
- Defense pack и отчёты JSON/HTML/XLSX.
- Профессиональный skill запрещает считать missing evidence как pass/fail и
  запрещает выдумывать пункт нормы.

## Блокеры стабильности

1. Coverage rulepack мал для полного СПДС-нормоконтроля: нет систематического
   покрытия форм, таблиц изменений, ссылочных стандартов, состава разделов и
   межлистовой согласованности.
2. `designation_cross_consistency` и `revision_consistency` пока layout/manual,
   без надёжного извлечения зон.
3. Retrieval adapter в синхронном review использует lexical source; vector
   обозначен как unavailable.
4. Без проиндексированного разрешённого экземпляра ГОСТ требование остаётся
   `review_needed`; это правильно, но public demo не показывает happy path.
5. Нет публичного обезличенного multi-file комплекта с ведомостью, листами,
   штампами, revisions и заранее подтверждёнными замечаниями.
6. Нет измеренных precision/recall для title-block/layout extraction и
   качества normalized remarks.
7. Нет живого browser smoke полного цикла: запустить → открыть evidence →
   подтвердить/отклонить → скачать отчёт → повторно открыть решения.

## Определение stable

Нормоконтроль стабилен, когда:

- область проверки и версия нормативной базы видимы в каждом отчёте;
- каждое замечание содержит объект, место, source, риск, действие и статус;
- отсутствие evidence никогда не становится соответствием или нарушением;
- computed и model-led выводы различимы;
- повторный прогон детерминированно сохраняет human decisions;
- публичный demo-комплект проходит end-to-end без private data;
- извлечение шифров, штампов, форматов и revisions имеет утверждённые метрики;
- Windows и macOS дают одинаковый normalized review contract;
- отчёты JSON/HTML/XLSX содержательно совпадают.

## План до стабильного

### P0 — публичная воспроизводимая приёмка

1. Собрать синтетический/разрешённый комплект ПД/РД:
   ведомость, 6–10 листов, корректные и ошибочные шифры, штамп, revision,
   текстовый PDF и скан.
2. Добавить короткие разрешённые requirement fixtures, не копируя полный текст
   стандарта.
3. Зафиксировать expected review items и human decisions.
4. Добавить CI-профиль normcontrol + `publication_check`.

Критерий выхода: clean clone даёт 0 failed и воспроизводимый отчёт во всех
трёх форматах.

### P1 — закрыть формальные пробелы

1. Реализовать cross-consistency `файл ↔ штамп ↔ ведомость`.
2. Реализовать revision consistency и устойчивую сегментацию зон листа.
3. Добавить OCR fallback с явной confidence/granularity.
4. Перевести vector requirement lookup на общий RAG contract и сохранить
   lexical exact-code channel.

Критерий выхода: manual остаётся только там, где действительно нужно
профессиональное решение, а не из-за отсутствующего extraction.

### P2 — расширить профессиональное покрытие

1. Согласовать матрицу СПДС/корпоративных правил по типам ПД, РД и ИД.
2. Добавлять rulepacks версиями с trace к источнику и датой действия.
3. Провести экспертную разметку замечаний и измерить precision/recall,
   severity agreement и citation precision.
4. Добавить browser/Windows release smoke и rollback решений.

Критерий выхода: утверждённый coverage matrix закрыт, метрики проходят порог,
а полный пользовательский цикл повторяется без ручной починки состояния.

## Риски и границы

- Эта ветка не публикует полный текст ГОСТ и клиентские комплекты.
- Текущие `55 passed` — доказательство offline contract, не живой
  профессиональной приёмки.
- Ветка stacked поверх RAG и smeta sync; отдельно от них clean build не
  гарантируется.
- Финальное заключение остаётся за инженером, модель формулирует и связывает,
  код извлекает, проверяет и трассирует.
