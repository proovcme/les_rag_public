# ALGO-notebook-study — инженерное чтение блокнота

## Назначение

Дать ЛЕС NotebookLM-подобный режим для любого выбранного датасета: не отвечать одним случайным top-k,
а сначала построить план чтения по карте блокнота, затем целево достать источники по разделам,
и только после этого дать модельную сводку. Чат получает ответ по широте запроса оператора,
правая панель — полный артефакт с найденными материалами, маршрутом чтения и пробелами.

Это не `project_summary_service` и не детерминированная подмена ответа. `notebook_study` — navigation
layer: блокнот и план помогают читать корпус, но evidence остаются найденные чанки и source-map.

## Точки входа

- `proxy/services/notebook_study_service.py` — trigger, reading plan, section retrieval pack,
  target-file enrichment по реальным file cards/folder groups, prompt-block и markdown artifact.
- `proxy/routers/chat.py` — подключает слой в обычный RAG-путь для явных broad-запросов по выбранной
  области: «расскажи/разбери проект», «инженерная сводка по блокноту», «что внутри датасета».
- `proxy/services/notebook_service.py` — источник карты датасета (`notebook_v1`).
- `proxy/services/retrieval_service.py` — для каждого раздела плана выполняется обычный hybrid retrieval.
- UI Совушки уже умеет показывать payload `artifact` в панели артефактов.

## Поток

1. Пользователь задаёт широкий исследовательский вопрос в выбранном scope/dataset.
2. `is_notebook_study_query()` включает слой только для явных study-интентов и не перехватывает смету,
   нормоконтроль, source lookup и точечные поисковые вопросы.
3. Перед сборкой study-pack чат best-effort готовит модельный `reader-pass` для выбранных датасетов:
   если `reader_output` уже есть, он используется сразу; если проход не успел за лимит
   `LES_NOTEBOOK_READER_ON_STUDY_TIMEOUT`, задача ставится в фон, а текущий ответ идёт по bootstrap-карте.
   Reader-pass — navigation, не evidence.
4. `build_dataset_notebooks()` читает deep-блокноты выбранных датасетов. Блокноты — navigation,
   `is_evidence=false`.
5. `build_reading_plan()` строит адаптивный компактный план: по карте блокнота выбираются только
   релевантные разделы, обычно до 4, а не весь список подряд.
6. Для выбранных разделов параллельно вызывается тот же `retrieve_chat_chunks()`, но с расширенным
   section query. Параллелизм задаёт `LES_NOTEBOOK_STUDY_PARALLELISM` (по умолчанию 3).
7. Для broad-study MetaDB-реестр строится как навигационный источник выбора файлов, даже если оператор
   не просил полный реестр. В prompt/видимый ответ полный реестр попадает только для явного
   inventory-запроса, чтобы не перетирать инженерный блокнот.
8. Слой делает второй retrieval-проход с точным `doc_filter=<file_name>` по bounded spread
   реально доступных file cards/folder groups. Он не предполагает паспорт, проектный том, таблицу
   или другой тип документа: код принимает в evidence только chunk, который сам называет выбранный
   файл (не basename guess). Чанк другого файла остаётся диагностикой retrieval, но не покрывает
   этот target-file шаг.
9. Найденные фрагменты добавляются в общий RAG-контекст; LLM получает `notebook_study` prompt-block
   и отвечает обычным модельным синтезом.
10. Payload получает:
   - `notebook_context.schema=notebook_study_v1`;
   - `retrieval_trace.dataset_reader_prepare`;
   - `retrieval_trace.notebook_study`;
   - `notebook_context.targeted_files[]` с именами файлов, причиной выбора и количеством найденных
     фрагментов;
   - `artifact.title=Инженерный блокнот` с найденными материалами, маршрутом чтения и пробелами.

## Границы

- Нет скрытого final-ответа без модели. Слой только организует чтение и retrieval.
- Нет answer-cache: ускорение достигается меньшим числом релевантных секций и параллельным retrieval,
  а не хранением готовых ответов.
- Нет объектных шаблонов состава работ.
- Числа не считаются этим слоем. Если вопрос про стоимость, объёмы или суммы — должны сработать
  сметные/табличные инструменты.
- Если раздел плана или точечно выбранный файл не нашёл источники, это пишется как пробел, а не
  заполняется догадкой.
- Полнота ограничена текущей индексацией: pending PDF и OCR-сканы останутся пробелами, пока не пройдут
  свой ingestion-путь.
- Reader-pass получает только фактические file cards, их folder-group summary и section map. Его
  JSON очищается от имён файлов, которых нет в карте корпуса; это навигация, а не доказательство.
- `research_guide.coverage` отдельно показывает число запланированных и успешно прочитанных file
  groups, а также chunks, отброшенные как пришедшие из другого файла. Поэтому hit в trace означает
  совпавший источник, а не просто непустой ответ retrieval.

## Форма первого продукта

На запрос «что в этом датасете?» модель должна по найденным источникам объяснить: какие материалы
представлены, что в них содержится, какие файлы/таблицы особенно важны и где граница чтения. Она не
должна подставлять ожидаемую отраслевую композицию или называть ограниченный bounded pass полным
прочтением корпуса.
