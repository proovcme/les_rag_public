## Алгоритм-доки (детерминированные ядра, 0 LLM)

Канон логики, которую LLM не трогает (числа/преобразования считает код, ADR-11). Читать
перед правкой соответствующего сервиса:
- **[ALGO-rag-best-practices.md](ALGO-rag-best-practices.md)** — рабочий стандарт LES для RAG/NotebookLM-подхода: датасет как source guide, navigation != evidence, model reader-pass, tool-loop, source refs, missing/blockers и golden checks на НС.
- **[ALGO-table-query.md](ALGO-table-query.md)** — счёт по ячейкам таблиц (суммы/кол-ва): типизация в Parquet → детерминированная агрегация по полному набору строк. Сервис `proxy/services/table_query_service.py`.
- **[ALGO-spec-to-bor.md](ALGO-spec-to-bor.md)** — спецификация (форма 9, ГОСТ 21.110) → ВОР работ (глагол по словарю). Сервис `proxy/services/spec_to_bor_service.py`.
- **[ALGO-asbuilt-intake.md](ALGO-asbuilt-intake.md)** — приёмка смонтированного объёма из исполнительных схем/чек-листов (сканов): рендер → авто-поворот → locate-then-read (vision-OCR — единственный LLM-шаг) → строки → журнал объёмов (status=pending). Сервисы `proxy/services/asbuilt_intake_service.py` (+ `asbuilt_ocr.py`), чат-канал `asbuilt_chat_service.py` (Совушка вызывает сама: «вытащи смонтированный объём из «<путь>»»), эндпоинт `POST /api/field/extract-asbuilt`, CLI `tools/asbuilt_extract.py`. Выбор vision-модели — бенч `tools/asbuilt_ocr_bench.py` (recall по якорям + латентность).
- **[ALGO-les-md.md](ALGO-les-md.md)** — `LES.md`/`ЛЕС.md`: файл-контекст папки (CLAUDE.md для ЛЕС). frontmatter (проект/объект/стадия/шифр/директивы/ignore) + тело→контекст чата; привязка папки к проекту, авто-черновик из скана. Сервис `proxy/services/les_md_service.py`, чат `les_md_chat_service.py` («пойми папку «<путь>»»), роутер `proxy/routers/les_md.py`.
- **[ALGO-fgis-price.md](ALGO-fgis-price.md)** — ФГИС ЦС: цена ресурса по коду из «Сплит-формы» (точное совпадение вместо top-k). `proxy/services/fgis_price_service.py` читает `data/price_base/*.parquet`, а `config/domain/pricebook_manifest.json` задаёт системную книгу, псевдонимы и скрытые дубли/черновики; `tools/build_smeta_service_rag.py` пересобирает `SMETA_SERVICE` только по видимым книгам и чистит свои сформированные карточки. Роутер `proxy/routers/prices.py` даёт одиночный `/lookup` и пакетный `/lookup-batch`; MCP — `les_price_lookup` и `les_price_lookup_batch`. Пакетный путь загружает книгу один раз и не превращает одну ЛСР в десятки последовательных обращений.
- **[ALGO-kac.md](ALGO-kac.md)** — КАЦ (конъюнктурный анализ цен): ≥3 КП на материал → выбор экономичного → цена в ЛСР; мост `needs_kac`→ФГИС ЦС. Сервис `proxy/services/kac_service.py`, роутер `proxy/routers/kac.py`, MCP `les_kac`.
- **[ALGO-smeta-ontology.md](ALGO-smeta-ontology.md)** — доменная онтология (ВОР/КАЦ/ЛСР/КС: что/зачем/из чего→во что); знание в `config/domain/smeta_ontology.yaml`+RAG, НЕ в весах. Сервис `proxy/services/smeta_ontology_service.py`, глоссарий `docs/smeta_ontology.md`, MCP `les_glossary`.
- **Model-first smeta catalog (ADR-13):** `norm_browser.browse_norm_catalog` читает актуальную ФГИС/ФСНБ typed-иерархию `family → collection → table`; перед поиском модель передаёт `smeta_scope_plan_v1` с собственными запросами и явным scope. Код буквально исполняет scope. Обычный shortlist проходит dedicated `dense + bm25_sparse` native RRF, обязательную rehydration из той же SQLite и configured cross-encoder с явным `rerank_status`, включая document batch; выбранный моделью `table_codes` вместо ranking возвращает полный selector-range таблицы по коду. Physical generation пишет отдельный manifest, `tools/smeta_rag_readiness.py` повторно проверяет оба канала/fingerprint/live RRF, а `tools/activate_smeta_rag_generation.py` атомарно публикует alias+active manifest без общей lexical projection. Статического перечня, предметного выбора сборника или выбора строки кодом нет. Живой contract проверяет `tools/smeta_rerank_ab_probe.py`. Канон: [ADR-13](ADR-13-smeta-session-workflow.md).
- **Model-first smeta chat:** `routers/chat.py` передаёт ordinary/document flow в `services/smeta_chat_application_service.py`; `services/smeta_agent_runner_service.py` выбирает `native|qwen_agent|google_adk`, а `document_workflow.SmetaNormToolSession` даёт всем движкам один stateful contract `search_norms_batch`/`read_norms_batch`/`submit_lsr_mapping`. Предметный mapping находится в `skills/smeta/references/document-mapping-agent.md`; встроенные RAG/MCP/search/code interpreter фреймворков не подключаются. Native сохраняет прежний Ollama transport и provider-enforced JSON mapping; Qwen-Agent ведёт function-call loop поверх Ollama `/v1` (32K) по одной активной строке, а `document_workflow` передаёт следующей строке накопленный журнал неизменённых модельных решений. `candidate_evaluations` хранит model-owned сравнение выбранной и открытой альтернативной карточки; код проверяет только форму/provenance. Принятая terminal mapping строка идёт отдельным SSE `smeta_row` в живую таблицу Совушки; черновые candidates туда не попадают. `professional_review.py` хранит append-only row/global/user-lock revisions, раздельные evidence budgets, conflict-only validator и golden metrics. После построчного loop та же модель обязательно создаёт global-review revision всей ВОР по compact card-map; полная спорная карточка лениво перечитывается tool-вызовом. Python не выбирает и не исправляет нормы. Автоматический расчёт всегда `priced_draft`; `/api/smeta-mappings/{revision_id}/lock` создаёт пользовательскую lock-ревизию и отдельный финальный расчёт. Raw function serialization нужна потому, что Nous text wrapper на Ollama `0.31.2` воспроизводимо возвращает `500 EOF`; Google ADK ведёт tools напрямую через Gemini и требует явное cloud consent + `GOOGLE_API_KEY`, без fallback и без сочетания tools с `output_schema`. Heartbeat, cooperative cancel между модельными/tool-ходами, attachment consumption, history artifact и idempotency остаются application-обязанностями. `tools/smeta_agent_benchmark.py` выполняет тот же global review; `tools/smeta_mapping_quality.py` готовит human-only очередь разметки и считает экспертные метрики вне production-ответов.
- **Repeatable smeta transport (0.24.46):** локальный native profile использует `qwen3.5:9b`, `temperature=0`, `LES_SMETA_DOCUMENT_SEED` (default `0`) и batch=5. `document_workflow` сортирует только model-authored запросы/tool-items и сохраняет seed в trace; scope и mapping не создаются кодом. `sovushka/state.py` хранит `session_id` в NiceGUI user storage, а `routers/chat.py` сохраняет recovered SSE в history и не отменяет запущенный workflow только из-за закрытия вкладки.
- **RAG readiness в GUI (0.24.0.369):** `proxy/services/rag_readiness_service.py` и `GET /api/rag/readiness[?dataset_id=...]` показывают alias→physical generation, contract/fingerprint, dense/sparse coverage, честный RRF state, прогресс sibling-build и отдельную готовность сметного индекса. «Документы» отображают общий статус в шапке и подробную карточку выбранного датасета; `quality_probe` называется диагностикой каналов и не выдаётся за подтверждение применимости норм.
- **Целостность датасета (0.24.17):** `GET /api/rag/datasets/{id}/integrity` сверяет исходники и их fingerprint, MetaDB, exact point ids Qdrant, named dense+sparse, lexical/FTS и текстовые страницы PDF. `POST .../integrity/repair` удаляет только orphan/stale проекции, помечает отсутствующие исходники и ставит только повреждённые документы в bounded parse-job. В «Документах» это одна операторская кнопка «Проверить и починить» с русским однозначным статусом; повреждение датасета не блокирует запуск ЛЕС.
- **Готовность и служебные датасеты (0.24.13):** `rag_readiness_service` считает прямую configured-коллекцию активной, восстанавливает ожидаемое покрытие из MetaDB и не требует отсутствующий advisory-marker при точном равенстве Qdrant/FTS. Сметный статус разделяет рабочую typed SQLite-базу и необязательный векторный поиск карточек норм. `system_dataset_service` идемпотентно создаёт закреплённые `Нормативы и чек-листы`, `Прайсы`, `Сметные источники`; Document Explorer ищет по ним и принимает файлы, а module scope подключает их только к профильному чату.

Боевая база одна: `data/smeta_base/les_smeta_base.sqlite` с typed `norm_key=<base_type>:<bare_code>`; unified parquet остаётся source/staging, raw ФГИС не читается расчётом напрямую. `tools/gesn_unify_base.py` и `tools/build_smeta_structured_base.py` дедуплицируют только тождественные ресурсы и до atomic replace требуют completeness floor и provenance каждой нормы/ресурса; невалидный rebuild оставляет canonical файл байт-в-байт прежним. `tools/smeta_release_baseline.py` связывает source/base/FSEM по SHA, собирает immutable Windows payload и умеет восстановить повреждённый clean-install state из проверенного пакета с резервной копией. `tools/fgis_full_update.py` ведёт атомарный checkpoint Сплит-форм, валидирует parquet перед resume и повторяет сетевые сбои; затем `tools/gesn_update_from_fgis.py` резюмирует префиксы `01..69`, собирает Parquet→SQLite→integrity→служебный индекс. - **`candidate_selection_service.py`** — общий контракт выбора кандидатов `candidate_selection_v1`: принимает уже найденный/ranked shortlist, объясняет score_parts, считает отрыв лидера и возвращает действие (`bind_top_candidate` только при ясном применимом лидере; иначе выбор модели или запрос данных). Не создаёт scope и не выбирает объект за модель.
- **Сметная декомпозиция** — текущий маршрут режима «Смета»: модель сама раскладывает объект на работы и вызывает инструменты; харнесс (`estimate_harness_service.run_estimate_harness`) даёт `search_norm`/`add_position`, `search_norm` использует общий `candidate_selection_service`, проверяет применимость норм, единицы и объёмы, а код считает только прошедшие gates. Если пользователь явно просит «придумай/прикинь/по допущениям», модель может задать геометрию и слоты как `assumptions`, а ответ маркируется как сценарная прикидка. `chat.py` отдаёт краткую операторскую сводку в `answer` и полную ресурсную сметную расшифровку в payload `artifact`. С 0.24.0.296 явное `сделай ЛСР/смету/стоимость` идёт в pricing-route даже для сырой ВОР: candidate-stage остаётся только для явного `этап 1/кандидаты/без денег`, а КАЦ/missing становятся построчным добором. С 0.24.0.297 `search_norm` остаётся read-only candidate retrieval, но лучше ранжирует model-facing нормы для live ЛСР: БАП светильника → малый `преобразователь/блок питания` (`ГЭСНм10/10`) против крупной UPS-системы; кабель → крепление накладными скобами против высоковольтного/бескрепёжного шума; гофра ПВХ внутри здания → indoor cable-protection route против `в земле`; коробка открытой проводки → ответвительная против клеммной без клемм/зажимов. С 0.24.0.298 `_smeta_review_structured_norm_choice` добавляет model-owned audit между черновым выбором нормы и РИМ-расчётом: ревизор может `approve|replace|unbound`, но `replace` валиден только шифром из candidates; код остаётся проверкой provenance и арифметикой. С 0.24.0.299 generic `finish/устройство` lookup сам уточняется до `primer/putty/wallpaper/painting` по тексту работы, чтобы модель видела same-operation отделочные нормы вместо общего шума. С 0.24.0.301 prompt boundary не откатывает проверенную ВОР-ГЭСН/lookup в candidates из-за отсутствия pricebook, harness считает явно выбранный моделью шифр после проверки в базе, parquet overlay не стирает старые `norm_name/norm_unit` пустыми значениями, а typed singletons получают broad nearby-навигацию. С 0.24.0.325 model-visible norm lookup для pricing-route расширен с 10 до 20 candidates, review больше не содержит stop-rule `unbound` для неточного демонтажа, а `search_norm` поднимает ремонтные `ГЭСНр63` для реечных потолков и `ГЭСН17-01-010-*` для ревизионных люков; защитную плёнку запрещено закрывать штукатуркой/грунтовкой/окраской. С 0.24.0.326 `finish/hatch` обрабатывает `люк/люч/ревизион` раньше окраски, а false-analog guard запрещает временное защитное укрытие считать декоративной/самоклеящейся ПВХ-плёнкой или натяжным потолком и запрещает ГКЛ-проём закрывать люками на крышах, фасадными/оконными/дверными проёмами. С 0.24.0.327 structured norm-choice не пропускает в расчёт candidates, которые lookup уже пометил `applicability_status=rejected` или `unit_compatible=false`; это provenance/validity gate, а не выбор нормы кодом. С 0.24.0.328 generic `finish` сначала маршрутизирует подготовку/ремонт потолочной поверхности в `ceiling`/ремонтный слой, даже если в тексте есть “лючки”, и rejected/unit-mismatch строки в ЛСР сохраняют исходное описание ВОР с причиной отказа вместо названия плохого candidate. С 0.24.0.329 direct selector/review audit сохраняют исходное `work_description`/`unit_hint` как видимое название/единицу строки ЛСР; norm title остаётся evidence, а не заменяет ВОР. С 0.24.0.330 `search_norm` показывает временное защитное укрытие через `protective_cover`/сборник 46 без декоративной ПВХ-плёнки/натяжных потолков и маршрутизирует штучные скобы гофры как `fastener`, а не `pipe`. С 0.24.0.331 smeta model-owned steps по умолчанию остаются на локальном MLX; global cloud key больше не переключает сметы молча, cloud используется только при явном smeta provider override. С 0.24.0.332 local structured norm-choice/review режет `lookup_results` на батчи (`LES_SMETA_NORM_CHOICE_BATCH_SIZE`), выбирает нормы моделью внутри каждого батча и склеивает результат с глобальными `lookup_index`; после live БАП 0.24.0.333 local default уменьшен до 2 строк, а `max_tokens` считается от строк текущего батча; с 0.24.0.334 эти батчи видны в `/api/chat/stream` как `smeta_batch`, в backend log как `[SMETA_BATCH]` и в операторском логе Совушки; с 0.24.0.335 крупные этапы до батчей видны как `smeta_step`/`[SMETA_STEP]`; с 0.24.0.336 local norm-choice получает компактное меню 5 candidates на строку и пишет prompt-size метрики `[SMETA_NORM_CHOICE]`. Старый объектный слой удалён: готовые объектные составы не являются маршрутом пользовательской сметы.

## Поток запроса (чат) и индексации

**Evidence boundary (0.24.0.342):** после обычного retrieval и context-window expansion
`evidence_packet_service` собирает `les.evidence_packet.v1`. Рендерер передаёт модели тот же
`Источник N` source context, который выходит в `source_map`; navigation, deterministic inventory
и tool results остаются отдельными слоями. Ответ несёт `evidence_packet`, а durable
`retrieval_trace.evidence_packet` содержит компактную provenance-сводку.

**Integrity core:** `rag_config` хранит `les.rag.index-contract.v2`; missing/mismatch
запрещает dense, а health показывает `dense_available=false`. Любой parser output перед embedding
проходит общий tokenizer budget и удаление mixed base64. Retrieval trace разделяет шкалы
dense/RRF/rerank, retry сохраняет backend, evidence context сначала покрывает разные источники,
а финальный ответ проверяется на существующие `Источник N`. `/retrieve-debug` ничего не дописывает;
прежние debug-based golden результаты не являются baseline.
Read-only `tools/rag_index_contract_audit.py` проверяет point fingerprints и покрытие нового
token/sanitation metadata; exit `1` означает, что старую коллекцию нельзя подписывать manifest-ом.

**Sibling migration:** `tools/build_rag_contract_sibling.py` создаёт отдельную native dense+sparse
коллекцию для всех indexed datasets по умолчанию. Старые vectors не копируются: payload text повторно
проходит общий final sanitation/token-budget gate и текущий embedder. Resume восстанавливает профиль
из immutable generation contract и до сборки сверяет remote model/backend/CoreML package/seq_len/
compute/fallback identity: совпадения размерности 1024 недостаточно. Progress пишется атомарно после
страниц, identity digest подтверждается для каждого source dataset. Dataset id/name всегда
перезаписываются из MetaDB; переживший миграцию legacy-domain `TABLE_SMETA` блокирует readiness.
Пунктуационный/noise child без BM25-токенов не получает synthetic token:
он попадает в audited exclusions с reason/hash; source/child/destination/exclusion accounting обязан
сойтись. `tools/rag_generation_supervisor.py` запускает resumable build как bounded-retry launchd job,
после полного отчёта строит FTS для physical generation, вызывает structural readiness, filtered
live native RRF по каждому dataset и только затем activation. Readiness требует `FTS chunks ==
destination points`; comma-separated build hosts не становятся одним invalid URL — live probe
identity-check'ит и выбирает один совместимый endpoint. `activate_qdrant_generation.py` повторно
сверяет live counts/channels/fingerprint, меняет stable Qdrant alias и атомарно публикует SQLite FTS
projection под тем же alias; при rollback старый FTS восстанавливается или новый alias-слой очищается.
Старые physical Qdrant/FTS generations не удаляются.

**System datasets (0.24.0.352):** MetaDB `datasets` хранит `dataset_scope` и `module_id`.
`system_dataset_service` владеет registry и module lookup; `SMETA_SERVICE_Index`,
`SMETA_RU_NORM_*` и GESN projection имеют `system/smeta`, видны отдельно в scope options и
автоматически добавляются только к smeta-turn. `document_router` отправляет `SMETA_SERVICE/**`
в этот dataset, а не в пользовательский `TABLE_SMETA_Index`.

**Qwen query contract (0.24.0.346):** документы Qwen-коллекции всегда получают raw embedding.
`backend.rag_config.prepare_query_for_embedding()` добавляет instruction только при явном
`RAG_QUERY_EMBEDDING_MODE=qwen-retrieval-v1`; baseline — `raw-v1`. `EmbedClient` применяет
контракт только к dense query, а `RetrievalTrace.query_embedding` и runtime config делают
режим воспроизводимым. Переключение требует A/B retrieval gate, но не reindex.

**Запрос:** `POST /api/chat` → `routers/chat.py` разрешает scope/route и исполняет explicit deterministic tools → формирует `EvidenceRequestContext` + `EvidenceRuntimeDeps` + `ResponseBoundary` без `globals()/locals()` → `chat_evidence_application_service` владеет общим evidence-flow: `retrieval_service` (semantic_cache → Qdrant) → `context_memory_service` + `dataset_memory_service` (deep-паспорт, typed-карта датасета и optional model reader-pass как фон/навигация, НЕ evidence; prompt-лимит датасетов) → для явного broad-study по выбранной области `notebook_study_service` строит reading plan и добирает section retrieval → optional `tool_harness_service` model-selected loop (модель выбирает read-only tools из shortlist, код исполняет, результат возвращается модели) → `saferag_service` (C-RAG: контекст + source-map `Источник N` + валидация фактов через MLX `/api/validate`) → `runtime_dispatcher` (MLX `/v1/chat/completions`, стрим) → ответ + `sources`/`source_map` + `latency_phases` + статус валидации + `scenario`/`answer_contract` + мягкий `answer_contract_check` + общий `workflow_plan_v1`; Совушка сохраняет план в metadata сообщения и показывает статус/финальность в чипах, а `workflow_id`/missing/actions — в техдеталях. Явный режим `smeta` использует отдельный `smeta_chat_application_service`; free/read-attachment LLM-пути подмешивают `session_memory` как фон. Для нормативных вопросов модель ведётся по маршруту `норма → пункт → вывод`: `dataset_memory_service` даёт навигационный атлас нормативных файлов, `retrieval_service` поднимает фрагменты по выбранной области, а `clause_lookup_service` остаётся deterministic final только для явных команд «найди пункт/раздел/приложение».

**Индексация:** upload → route/convert → parser-specific nodes → единый final sanitation/token-budget gate → embedding по совместимому `index-contract` → Qdrant + lexical projection + MetaDB. Parser-specific chunking улучшает границы, но не может обойти фактический лимит tokenizer. Raw CAD/BIM остаётся вне текстового RAG и сначала переводится в canonical JSON/JSONL projection.

(v0.24.0.302+, reliability 0.24.0.344)** — единый PDF project source-map без reindex: читает MetaDB PDF-документы датасета, пишет sidecars в `_les_pdf_extract`, объединяет `drawing_manifest`, `pd_rd_manifest`, shared table и electrical readers в `project_pdf_extract_v1`. Роли/дисциплины берутся из разделённых filename/cipher-кодов и whitelist, а не подстрок; coverage разделяет attempted/successful, итог имеет `ok/partial/failed/empty`, bounded warnings/refs/register несут total+truncated, `dataset_id` path-safe. Shared table classifier требует составные признаки кабеля и ВОР, чтобы таблицы технических руководств не становились проектной навигацией. Пользовательское имя слоя: **Л.И.С.Т. · Локальный индекс структуры томов**. Эндпоинты: `/api/rag/datasets/{dataset_id}/pdf-extract/status`, `/run`, `/summary`; `dataset_memory_service` добавляет compact `project_pdf_extract` в model brief как navigation-not-evidence; `sovushka/pages/documents.py` показывает операторскую панель в порядке `реестр файлов → Mermaid-карта → PDF/тома` и сразу применяет фильтр датасетов.
- **`proxy/services/project_document_registry_service.py` (0.24.0.376)** — read-only JSON-проекция `Документация → проект → стадия → виртуальный том → раздел → документ`. Выпущенный PDF якорит том по каноническому шифру+дисциплине; вспомогательные документы присоединяются по identity/discipline/stage, путь — последний fallback. Том показывает basis/confidence и никогда не склеивает файлы. Договоры/КП/сметы/переписка — связанные сущности. API: `/document-registry/{build,read}`, `/virtual-volume?index=...`; model tool `assemble_project_volume`.
- **`proxy/services/project_table_registry_service.py` (0.24.0.376)** — JSONL-реестр таблиц Л.И.С.Т. с fail-closed evidence identity. Search cards — navigation; 32-hex `table_id` связывает SHA-256 PDF, page, bbox, full header, algorithm/detector versions. Exact read проверяет fingerprint/geometry/header и возвращает `stale` при любом drift; stale tool не выдаёт evidence, API — `409`. API: `/table-registry/{build,summary}`, `/tables/search`, `/tables/{table_id}`; model tools `search_project_tables`, `read_project_table`.
- **`proxy/services/doc_type_classifier.py` (v0.17)** — filename→doc_type/discipline (вынесен из unified, чтобы runtime-эндпоинты не тянули весь харнесс).
- **`proxy/services/doc_extract_service.py`** — sidecar-извлечение PDF/DOCX/XLSX (без OCR; `.xls`→honest `legacy_unsupported`). **`sovushka/answer_render.py`** — чистые render-хелперы (source-chips, evidence-секции, citation/conflict, `answer_copy_text` для «Копировать»).
