# Не просто фрагменты: почему LES идёт к блокнотам, картам и проверяемым расчётам

RAG часто описывают слишком бедно: взяли документы, порезали на фрагменты, положили в поисковый индекс, нашли похожие места, отдали модели. Для демо этого хватает. Для строительного проекта, нормоконтроля или сметного расчёта — уже нет. Там модель должна понимать не только “какой фрагмент похож”, но и что это за корпус, какие в нём роли документов, где таблицы, где нормы, где чертежи, где расчётная форма, где источник, а где служебный мусор.

Поэтому нам полезно смотреть не только на классический поиск по базе знаний, но и на продукты вроде NotebookLM. Не потому что нужно копировать интерфейс, а потому что там хорошо видна правильная мысль: пользователь работает не с безликой кучей фрагментов, а с блокнотом источников.

## Что примерно делает NotebookLM

Google описывает NotebookLM как блокнот с ИИ, который отвечает по выбранным пользователем источникам. В публичном описании подчёркнуты несколько вещей: пользователь выбирает документы, система помогает делать краткие обзоры, задавать вопросы, генерировать идеи, а ответы сопровождаются ссылками на оригинальные источники для проверки. В Workspace-описании NotebookLM отдельно говорит про загруженные источники, ответы со ссылками, аудиообзоры, карты идей и превращение документов в интерактивное рабочее пространство.

Источники, которые я смотрел:
- [Google Workspace: NotebookLM](https://workspace.google.com/products/notebooklm/)
- [Google Blog: NotebookLM Discover Sources](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-discover-sources/)

Если снять продуктовый слой, архитектурный смысл такой:

1. Есть не просто поиск, а выбранная область знания.
2. Есть источники, у которых есть границы и роли.
3. Есть первичная карта материала: краткое содержание, темы, вопросы, связи.
4. Есть ответы, привязанные к источникам.
5. Есть артефакты вокруг корпуса: аудио, mind map, заметки, сохранённые выводы.

Это не значит, что внутри нет нарезки документов. Конечно, есть фрагменты, поиск, ранжирование и контекст для модели. Но пользователь и модель живут уровнем выше: “вот мой блокнот, вот источники, вот карта, вот что из этого можно делать”.

## Почему одних фрагментов мало

Фрагмент сам по себе не знает, зачем он нужен.

Он может содержать строку нормы, кусок пояснительной записки, обрыв таблицы, страницу спецификации, JSON из базы, часть письма, распознанный текст со скана или служебный файл индекса. Для поиска всё это часто выглядит одинаково: текст с какими-то словами. Но для инженера это разные сущности.

Проблемы начинаются сразу:

- модель видит похожий фрагмент, но не понимает, из какого слоя он пришёл;
- служебные файлы всплывают рядом с полезными;
- таблица без структуры превращается в художественную прозу;
- нормативный пункт путается с проектным описанием;
- сметная форма путается с исходной спецификацией;
- цена из допущения выглядит так же, как цена из проверенного расчёта;
- модель начинает “добирать” недостающий смысл сама, потому что корпус не дал ей навигацию.

Это и есть та самая беда: мы просим модель быть профессионалом, но даём ей стопку бумажек без оглавления. Потом удивляемся, что она уверенно открыла не ту папку.

## LES: датасет как блокнот

В LES следующий слой — воспринимать каждый датасет как маленький блокнот:

- паспорт датасета;
- inventory файлов;
- типизированная память;
- карточки файлов;
- граф источников;
- маршруты поиска;
- пояснения оператора для модели;
- читательский проход по корпусу;
- артефакты для человека.

Это не доказательство само по себе. Это карта местности.

Доказательства остаются в источниках: фрагменты документов, строки таблиц, CAD/BIM-свойства, нормативные пункты, расчётные трассы. Но карта помогает модели понять, куда идти. Разница простая: карта не доказывает, что дверь открыта; она показывает, где эта дверь находится.

## Веса и роли вместо одной каши

У документа должны быть роли и слои:

- `text` — пояснения, условия, описания;
- `tables` — спецификации, ВОР, количества, строки;
- `calculations` — ЛСР, формулы, стоимостные итоги;
- `normative` — СП, ГОСТ, ГЭСН, ФСЭМ, ФСБЦ, сплит-формы;
- `drawings` — листы, схемы, геометрия;
- `cad_bim` — элементы, свойства, связи модели;
- `estimate` — сметные формы и прежние расчёты.

Дальше появляются веса:

- служебный файл ниже живого документа;
- нормативный корпус выше проектной болтовни для вопроса “по нормам”;
- таблица выше prose для вопроса “сколько”;
- проверенный расчёт выше допущения для вопроса “итог”;
- выбранный датасет выше общей базы знаний;
- комментарий оператора помогает навигации, но не становится фактом.

Это не “код отвечает за модель”. Это нормальная уборка комнаты перед работой. Модель всё ещё думает сама, но ей больше не приходится отличать ГЭСН от `.pdf_preprocess_state.json` по запаху.

## Баланс кода и промта

Промт должен задавать профессиональное поведение:

- читай источники;
- строй ход рассуждения;
- отделяй факт от предположения;
- не называй сценарий финалом;
- не путай поставку и работу;
- если есть измеримая ВОР, пытайся дать стоимость;
- если источник конфликтует, покажи развилку.

Код должен делать скучную, но проверяемую работу:

- разбирать файлы;
- строить карту датасета;
- нормализовать числа и единицы;
- считать суммы, проценты, НДС, НР/СП;
- связывать строки таблиц;
- хранить происхождение данных;
- строить Excel/CSV/ЛСР-артефакты;
- показывать карту источников и расчётную трассу.

Граница важная: код не должен выбирать профессиональный смысл за модель. Он не должен из ключевого слова “кабель” сам собрать смету. Но код обязан подготовить поверхность, на которой модель не поскользнётся: показать, где спецификация, где ВОР, где нормы, где цены, где пустота.

## Мягкий намёк на сметы

Сметы — хороший стресс-тест этой архитектуры.

Если дать модели только спецификацию СКС, она может сказать: “цен нет, сметы нет”. Формально осторожно, практически бесполезно. Если дать ей карту “спецификация → ВОР → нормы → ресурсы → цены → расчётная трасса”, она уже работает как сметчик:

- из поставки строит ВОР;
- отделяет материалы от работ;
- ищет нормативный маршрут;
- показывает, что закрыто РИМ, а что сценарно;
- выводит ЛСР-подобную форму;
- не превращает missing в 0;
- не называет допущение финальной сметой.

То же с ФСНБ. Если в базе знаний лежит сырой `A_SRF_F.json.md`, модель видит техническую внутренность базы. Если рядом есть понятная карточка “таблица норм/расценок ФСНБ”, “таблица ресурсов нормы”, “иерархия разделов и таблиц”, она уже понимает маршрут чтения. Не магия. Просто человеку тоже проще работать с оглавлением, а не с мусорным пакетом файлов.

## Что LES должен делать дальше

Правильное направление:

1. Датасет получает паспорт и карту.
2. Каждый файл получает роль и слои.
3. Служебный шум понижается, но не удаляется.
4. Оператор может написать пояснение для модели.
5. Модель читает карту перед ответом.
6. Retrieval идёт по маршруту, а не по одной похожести.
7. Код считает только проверяемые вещи.
8. Ответ показывает источники, статусы и артефакты.

Именно так LES перестаёт быть “чатом поверх базы знаний” и становится инженерным блокнотом: модель думает, источники доказывают, код считает, человек видит карту и может вмешаться.

Простые фрагменты дают память. Блокноты дают ориентацию. Для строительства это не роскошь, а санитарный минимум, иначе любая умная модель быстро превращается в уверенный генератор красивой ерунды.
