# Алгоритм: как делается смета в ЛЕС (единый поток — для оператора)

Этот документ **сшивает** разрозненные сметные ALGO-доки в один связный поток «от объёма работ
до общей цены». Детали каждого кирпича — в своём доке (ссылки по тексту); здесь — как они стыкуются
и **как этим пользоваться**. Числа считает КОД (ADR-11, 0 LLM в расчёте); каждое число цитируемо и
проверяемо тестом. Эталон сквозной проверки — позиция **«Устройство обрешётки» (ГЭСН 12-01-034-02)**,
которая воспроизводится бит-в-бит: **Всего по позиции = 11813.04 ₽** при объёме 0.61.

## 0. Архитектурное решение: первая ЛСР до аудита

Сметный модуль LES имеет четыре ортогональных слоя:

```text
модель + smeta skill + prompt  → профессиональные решения
RAG/tools                      → нормы, ресурсы, цены и источники
код                            → единицы, РИМ, НР/СП, НДС, provenance и XLSX
последующий аудит              → замечания или новая ревизия
```

Единственный основной поток `estimate`:

```text
SOURCE_READING
  → BOR_DRAFT
  → MODEL_RAG_NORM_SELECTION
  → FIRST_MONEY_LSR
  → OPTIONAL_AUDIT
  → OPTIONAL_REVISED_LSR
```

Это архитектурный инвариант, а не настройка качества:

- модель выбирает работы, нормы, аналоги, покрытия и ценовой маршрут;
- RAG и tools показывают фактические данные, но ranking не является решением;
- код проверяет существование выбранного кода, единицы и арифметику, затем сразу строит первую ЛСР;
- отсутствие цены или нормы оставляет видимую partial/MISSING-строку и не отменяет рассчитанную часть;
- resource/component review, проверка крупнейших позиций и пользовательское согласование выполняются
  только после первой ЛСР;
- последующий аудитор не удаляет и не переписывает решения модели в той же ревизии;
- запрещено ставить перед `FIRST_MONEY_LSR` code-side selector, обязательное число кандидатов,
  обязательный review, общий quality gate или лимит, завершающий модель до её решений.

Дополнительный `candidate_review` остаётся отдельным режимом по запросу пользователя и не подменяет
`estimate`. Проверенная пользователем таблица может стать входом новой ревизии, но ручное согласование
не является обязательным условием первой денежной ЛСР.

Границы основного потока:

- `SOURCE_READING`: модель читает все приложенные источники и фиксирует, что каждый документ даёт
  расчёту: работы/объёмы, форму, НР, СП, РКС/МПРКС, коэффициенты, КП/КАЦ или ограничения.
- `BOR_DRAFT`: модель строит ВОР/разделы из ТЗ, ВОР, спецификации, PDF/XLSX/DOCX и истории. Код не
  добавляет работы и не выбирает состав операций.
- `MODEL_RAG_NORM_SELECTION`: для строк ВОР модель строит нормируемые работы и кандидаты
  `ГЭСН`/`ГЭСНм`/`ГЭСНп`/`ГЭСНр`/`ГЭСНмр`. Если одна строка ВОР имеет несколько кандидатов,
  человеческий блок `Данные ТЗ / ВОР` повторяется в каждой строке, а связь держится стабильным
  `vor_row_id`. Если несколько строк ВОР покрываются одной нормой, строка нормы хранит список
  `source_row_ids` и пояснение, какие исходные работы объединены.
- `FIRST_MONEY_LSR`: сразу после решений модели код раскрывает ресурсы выбранных норм, применяет
  доступные цены, ФСЭМ, НР/СП и формирует денежную ЛСР. Она может иметь пустые цены или placeholders, если нет
  цены ресурса, индекса, коэффициента или КП. Такой ноль не является фактической ценой и обязан
  иметь примечание `КАЦ/КП/ручной ввод/коэффициент не задан`.
- `OPTIONAL_AUDIT`: модель или пользователь проверяет аналоги, ресурсы, dominant positions,
  коэффициенты, coverage и gaps уже созданной ЛСР. Проверка не отменяет исходный артефакт.
- `OPTIONAL_REVISED_LSR`: пользователь может внести коэффициенты условий производства, снижения
  производительности, техчасти сборников, проектные усложняющие факторы и реквизиты КП/КАЦ; ЛЕС
  пересчитывает ту же структуру, а не выбирает нормы заново.
- `priced_final` является характеристикой ревизии, а не разрешением показать результат.

Формулы ЛСР РИМ по этому workflow:

- строка нормы: графа 7 = графа 5 × графа 6;
- ОТ(ЗТ) рабочих: количество = объём нормы × норматив трудозатрат × коэффициенты, сумма = количество × цена;
- ЭМ — стоимость машин без ФОТ машинистов;
- ОТм(ЗТм) — ФОТ машинистов, добавляется рядом с машиной, если ФСЭМ даёт экипаж/трудозатраты;
- М — материалы из нормы или пользовательские/КАЦ позиции;
- прямые затраты = ОТ + ЭМ + ОТм + М;
- ФОТ = ОТ + ОТм;
- НР = ФОТ × ставка 812/пр / 100;
- СП = ФОТ × ставка 774/пр / 100;
- всего по позиции = прямые затраты + НР + СП.

В присланной форме есть текстовая формула `прямые + ФОТ + НР + СП`, но числовой пример сходится как
`прямые + НР + СП`; до отдельного решения нельзя молча удваивать ФОТ. Реализация должна считать как
`прямые + НР + СП` и оставлять audit-note, если источник требует иной трактовки.

Вывод: стабильность одного рублёвого числа не является критерием качества. Критерий качества —
зафиксированный вариант подбора норм, прозрачные placeholders, closed/open gaps и расчётная trace.

Поиск нормы выполняется по маршруту:

```
семейство работ -> группа сборников -> сборник -> раздел/таблица сборника -> конкретная норма
```

Подбор не ограничивается `ГЭСН` и `ГЭСНм`: для пусконаладки, ремонта и монтажного ремонта нужно
проверять также `ГЭСНп`, `ГЭСНр`, `ГЭСНмр`. Таблица кандидатов должна быть Excel-friendly:
фильтруемые колонки `Данные ТЗ / ВОР` и `Соответствие данным ТЗ / ГЭСН`, стабильные ID строк и
понятное поле статуса применимости. Финал этого этапа — форма для применения ресурсов и цен, а не
рублёвый итог.

Ведомость добора после первого ЛСР относится к ресурсам, которые уже попали в выбранную норму или
пользовательскую ресурсную строку, но не нашли цену/индекс в сплит-форме, локальной книге или КП.
Это не список “того, что модель не поняла”: нераспознанные работы остаются в нормативных gaps и
возвращаются на этап ВОР/кандидатов.

Режим качества:

- `rough_cost`: прикидка по уровню стоимости, допускает assumptions и диапазоны.
- `stage_p`: расчёт под стадию П, требует основных проектных решений, разделов, объёмов и
  нормативного маршрута, но может иметь добор по коэффициентам/КАЦ.
- `stage_rd`: смета под РД, требует выбранных норм, закрытых ресурсов/цен, коэффициентов,
  региона/периода и trace; только этот режим может быть `priced_final`.

## 1. Поток end-to-end (с формулами)

```
ВОР (объёмы работ)                                    ← что и сколько делаем
  │  каждая работа → код нормы ГЭСН
  ▼
норма ГЭСН (gesn_service, база 42408 норм из ФГИС ЦС) ← расход на единицу
  │  расход × объём → строки ресурсов (труд / машины / материалы)
  ▼
цены ресурсов
  │  есть код в «Сплит-форме» ФГИС ЦС (локально)      → fgis_price.lookup   [[ALGO-fgis-price]]
  │  нет кода (материал)                              → КАЦ (≥3 КП)         [[ALGO-kac]]
  ▼
агрегация по видам:  ОЗП=Σтруд · ЗПМ=Σмашинисты · машины · М=Σматериалы
  │  ЭМ = машины + ЗПМ
  ▼
стеснённость (k к ОЗП и ЭМ; материалы не трогаются)  [[ALGO-stesnennost]]
  ▼
прямые = ОЗП + ЭМ + М                ФОТ = ОЗП + ЗПМ
  │
  ▼
НР / СП по виду работ (nr_sp, Приказы 812/пр · 774/пр; оба % от ФОТ)
  │  НР = ФОТ · нр%      СП = ФОТ · сп%
  ▼
Всего по позиции = прямые + НР + СП    (lsr_assembly.compute_position)  [[ALGO-lsr-assembly]]
  │  свод позиций по разделам → lsr_assembly.assemble
  ▼
ИТОГО СМР = Σ(прямые + НР + СП)        ← объектная смета: object_estimate  [[ALGO-object-estimate]]
  + непредвиденные 2%
  + НДС 20%
  ▼
ВСЕГО (общая цена с НДС)
```

**Бухгалтерия позиции** (выверена на эталоне, обрешётка, объём 0.61):

| Величина | Формула | Эталон |
|---|---|---|
| ОЗП | Σ labor | 3750.23 |
| ЗПМ | Σ machinist (ОТм) | 458.68 |
| ЭМ | машины + ЗПМ | 992.40 |
| М | Σ material | 83.62 |
| Прямые | ОЗП + ЭМ + М | 4826.25 |
| ФОТ | ОЗП + ЗПМ | 4208.91 |
| НР | ФОТ × нр% (109, «Кровли») | 4587.71 |
| СП | ФОТ × сп% (57, «Кровли») | 2399.08 |
| **Всего** | Прямые + НР + СП | **11813.04** |

Граница ответственности: **позицию** (до «Всего по позиции» + свод по разделам) считает
`lsr_assembly`; **хвост объектной сметы** (СМР → непредвиденные → НДС → ВСЕГО) добавляет
`object_estimate_service.estimate` (`smr → contingency 2% → before_vat → vat 20% → grand_total`).

Актуальный чатовый маршрут «Смета» (0.24.0.20+) — `estimate_harness_service`: модель сама
раскладывает задачу на работы, а код даёт инструменты `search_norm`/`add_position`, проверяет
единицы/применимость/объёмы и считает. С 0.24.0.84 `search_norm` получает кандидатов из
`smeta_norm_store_v3` — in-memory SQLite/FTS-проекции существующих ГЭСН/ФСНБ/ТЕР источников
с норм-карточками: база/сборник/единица, provenance, виды ресурсов, domain hints по семье работ,
элементу/действию и русская `model_card` с условиями применимости (например группа грунта,
глубина, крепления, масса элемента, способ производства работ). Это не объектный шаблон и не
второй источник истины: индекс только помогает модели получить качественный shortlist норм и
спросить недостающие параметры, а все рубли/объёмы остаются результатом code guards.

С 0.24.0.85 `add_position` использует условия выбранной нормы как gate итоговой суммы. Если физический
объём задан явно (`200 м3`, `664 711 кг`), код всё равно считает строку, но `_finalize()` оставляет
ответ `partial`, пока не подтверждены критичные условия применимости нормы: для земляных работ это
может быть группа грунта, глубина, крепления и ширина/сечение. Эти вопросы уходят в `norm_questions`
и показываются модели/диалоговой памяти по-русски. Generic-условия вроде общего способа производства
остаются в карточке нормы как подсказка модели, но не превращаются в обязательный стопор для каждой
позиции.

С 0.24.0.339 `price_requirements` также закрывают только статус finality: строка и рассчитанная
часть остаются в trace/artifact, но `final_total` не создаётся, пока не закрыты ФГИС/КАЦ/тарифные
цены. Нормативный pipeline и runtime-reader консервативно схлопывают одинаковый ресурс по
коду (или нормализованному имени без кода), единице, расходу и явной цене; это защищает старые
SQLite/Parquet базы от двойного учёта, не меняя модельный выбор нормы, работ или применимости.

С 0.24.0.86 нормальный следующий слой — **навигация по нормам, не объектные пресеты**.
`smeta_norm_store_v4` добавляет к каждой норме `navigation`: сборник/подраздел, вопросы применимости,
РИМ-границу и несколько `nearby_norms` из того же сборника/контекста. `search_norm` возвращает
общий `norm_navigation` по shortlist: какие сборники всплыли, какие вопросы нужно задать, что делать
дальше. Блокнот ГЭСН в prompt теперь напоминает модели ход: семейство работ → вероятный сборник →
единица измерения → условия применимости → только потом bind/add_position. Код не добавляет разделы
за модель и не превращает “дачу” в шаблон; он даёт модели карту, а деньги считает только после
инструментальной проверки.

## 1а. Доказательная трасса и форма ЛСР РИМ (Приложение № 3)

Поверх расчёта строится **РИМ-трасса** (`rim_lsr_trace_service`) — те же числа, разложенные по графам
2-12 формы ЛСР с происхождением каждой цены (текущая ФГИС ЦС / база×индекс / КАЦ / явная / `missing`).
Это не второй калькулятор: `build_position_trace` берёт норму и цены тем же путём, что `lsr_assembly`,
и раскладывает одну позицию в проверяемые строки (работа → ОТ(ЗТ)/ЭМ/ОТм/М → прямые/ФОТ/НР/СП/Всего).

Трасса рендерится в XLSX по форме **Приложения № 3 к Методике 421/пр** (форма ЛСР РИМ,
`rim_trace_xlsx_service`); числа НЕ пересчитываются — рендер берёт ГОТОВУЮ трассу:

```
одна позиция         → build_position_trace → render_trace_xlsx  → POST /api/lsr/rim-trace/export
многопозиц. смета     → build_lsr_trace      → render_lsr_xlsx    → POST /api/lsr/lsr-trace/export
                         │ позиции по разделам (поле section), непрерывная нумерация,
                         ▼ «Итого по разделу N» + общий свод «ВСЕГО по смете»
```

Шапка формы — стройка/объект/ЛСР №/ресурсный метод/уровень цен/субъект + разбивка сметной стоимости
(ОЗП/ЗПМ/нормативные чел.-ч рабочих и машинистов). Свод многопозиционной = Σ позиций (код, не LLM).
Gold сохраняется: позиция 11813.04, смета 2×позиции = 23626.08. ЛСР РИМ = **Приложение № 3**.
Индекс для `база×индекс` — из ФГИС ЦС, официально из писем Минстроя ИФ/09
([[minstroy-indices-source]], бэклог). Детали графов и свода — [[ALGO-lsr-assembly]].

## 1б. Model-first smeta harness

Текущий режим «Смета» не строит готовый объектный состав. Модель получает общий LES prompt,
сметный prompt, ГЭСН-блокнот и contract инструментов; дальше сама раскладывает объект в работы.
Харнесс исполняет только инструменты и gates: `search_norm` подбирает кандидатов нормы, `add_position`
проверяет применимость/единицы/слоты и считает объём/деньги кодом.

С 0.24.0.30 для металлического монтажа восстановлен мост к монтажной базе: `ГЭСН38` и `ГЭСНм38`
различаются как разные разделы notebook/search, а `metal_assembly` допускает `ГЭСНм38`. Если в ТЗ
есть масса (`кг` или `т`), она нормализуется в слот `mass_t`; тоннажная позиция считается через
обычный ЛСР/ресурсный калькулятор, а не через текст модели. С 0.24.0.47 числовые слоты из Office/DOCX
принимают пробелы, NBSP, запятую/точку как десятичный или тысячный разделитель (`664 711,12`,
`664.711,12`, `664,711.12`), без объектных спец-веток. Явные физические объёмы работ
(`volume_m3`, `area_m2`, `mass_t`, `piece_count`) могут стать количеством позиции напрямую:
например `200 м3` для нормы с измерителем `100 м3` даёт `qty=2`, без требования ширины/глубины
только ради пересчёта уже заданного объёма.

С 0.24.0.49 прямые физические количества получили защиту от умножения одной и той же работы:
если планировщик несколько раз предлагает один `code` с тем же direct-слотом (`mass_t`/`volume_m3`/
`area_m2`/`piece_count`) и тем же физическим объёмом, харнесс считает первую позицию, а остальные
помечает `skipped_duplicate` до отдельной доли или отдельного объёма. Для таких direct-расчётов
видимый заголовок не показывает служебную площадь объекта, которую могла набросать модель-планировщик.

С 0.24.0.50 smeta harness получает отдельный role-pack **«Опытный сметчик РИМ/ГЭСН»**:
`config/prompts/smeta_estimator_role.json`. Это JSON-контракт, а не скрытая строка в коде: роль,
правила, анти-паттерны, direct-quantity policy и `output_contract.schema=smeta_work_plan_v1`.
`prompt_registry_service` подмешивает role-pack в системный prompt, а `/api/prompts` показывает его
оператору. Дальше этот паттерн можно повторять для других ролей: skill объясняет профессию, JSON
задаёт машинный контракт, код проверяет результат.

С 0.24.0.137 role-pack снова тонкий: статусы результата, типы источников цены, обязательные
capabilities ответа, порядок visible-секций, колонки формы развилки исходных объёмов и таблицы
РИМ/ГЭСН vs рынок. Профессиональная методика живёт в `skills/smeta/SKILL.md`, case-specific числа —
только в fixtures/tests. `estimate_math_service` получил generic arithmetic/quantity audit helper:
русские числа, кг↔т, суммы строк, проценты, partial matches и trace; helper не выбирает работы,
нормы или договорный объём.

С 0.24.0.142 добавлен базовый слой **спецификация → ВОР**. Если пользователь дал спецификацию
оборудования, материалов, изделий, кабелей, труб, МАФ, металлоконструкций или смешанную таблицу,
модель не считает её готовой сметой: сначала разделяет поставку и работы, сохраняет parent/child
структуру, строит ВОР-кандидат с основаниями и quantity trace, а уже потом выбирает нормативный
маршрут. `quantity_trace_service` считает русские числа, `количество на 1 изделие × количество
родителя`, простые kg↔t/alias-конверсии и статус `missing_quantity`; сервис не выбирает состав работ,
нормы, применимость и договорный объём.

С 0.24.0.146 добавлен следующий промежуточный слой **ВОР → нормируемая ВОР → таблица подбора норм**.
Это ответ на рабочий контур с Excel round-trip: модель переводит человеческую строку ВОР в
нормируемые действия и предлагает кандидаты ГЭСН/ГЭСНм с группой сборников, разделом, измерителем,
пересчитанным объёмом и статусом применимости; пользователь может удалить лишние нормы, добавить
свои и загрузить таблицу обратно. Одна строка ВОР может раскладываться на несколько ГЭСН, если это
следует из технологии или состава норм. Кандидат нормы не является финальным РИМ-расчётом: расчёт
идёт только по подтверждённым или явно выбранным строкам, а отсутствующая цена ресурса остаётся
ценовым добором, не нулевой ценой.

С 0.24.0.196 порядок ЛСР РИМ уточнён по рабочей схеме сметчика: после подтверждённой таблицы
подбора норм форма заполняется не как плоский список работ, а как последовательность строк
`раздел → выбранная норма → коэффициенты → ОТ/расшифровка → ЭМ/ОТм/расшифровка → М/расшифровка →
прямые → ФОТ → НР → СП → всего по позиции → КАЦ/missing → итоги раздела → итоги сметы`. Графы 1-12
остаются формой ЛСР РИМ; renderer раскладывает готовую трассу, а модель отвечает за ВОР, выбор
нормативного маршрута и применимость.

С 0.24.0.51 direct quantity не проходит `magnitude_guard` по геометрии объекта. Guard остаётся для
формульных объёмов (где ошибка площади/глубины может дать ×100), но пользовательское `volume_m3`,
`mass_t`, `area_m2` или `piece_count` считается авторитетным физическим количеством. Это закрывает
случай, когда опытный role-pack честно ставит служебную маленькую площадь, а уже заданные `200 м3`
траншеи раньше отвергались как “слишком много для пятна”.

С 0.24.0.52 граница direct quantity уточнена: объектная `площадь 200 м2` — это метаданные объекта,
а не автоматический `area_m2` для каждой м²-позиции. Direct `area_m2` применяется только для явного
запроса стоимости конкретной работы с количеством. Role-pack и smeta skill фиксируют best-practice
из Codex skills/prompts/loops: skill = профессия и workflow, JSON role-pack = машинный контракт,
tools/data-service = доступ к нормам и источникам, код = арифметика/валидация/provenance. Поэтому
новые объектные ситуации не закрываются if-шаблонами; системное направление — нормализованная
`ГЭСН sqlite light`/витрина кандидатов как инструмент для модели.

С 0.24.0.53 уточнена философия петли: модель — сметчик-оркестратор, расчётные сервисы — её
инструменты. Код не подменяет сметное рассуждение, но и не принимает JSON-заглушку модели как
evidence. Площадь/габариты для геометрии берутся только из текста пользователя/файла/истории;
если broad object приходит без площади, м²-позиции не ищут нормы и не считают микросмету на `1 м2`,
а возвращают `needs_input` по площади/габаритам. Видимый smetnik-layer — это второй ход модели по
tool-result payload, а не соседняя подпись к таблице: модель видит computed/pending/missing slots и
объясняет следующий шаг. Для продолжения диалога `retrieval_trace_json` хранит компактный
`smeta_dialog_state_v1`, чтобы следующая реплика модели видела прошлый расчётный статус, а не только
текст ответа. При `partial` модель не получает рубли как разрешённый факт, чтобы не продавать
рассчитанную часть как готовый ответ.

С 0.24.0.55 добавлено явное исключение для пользовательского разрешения на сценарий: если в текущем
диалоге есть «придумай», «прикинь», «по допущениям», «типовой вариант» и т.п., модель может задать
площадь/габариты и критичные слоты как `assumptions`. Это не отменяет gates: нормы, единицы,
формулы и деньги всё равно считает код, а видимый ответ обязан пометить результат как
«Сценарий по допущениям», не проектную смету. Без такого разрешения модельная `area_total_m2`
остаётся не evidence и не создаёт геометрию.

С 0.24.0.56 видимый сметный слой и `smeta_dialog_state_v1` переводят внутренние ключи параметров
в русские формулировки: `wall_length_m` → «длина/периметр стен», `area_total_m2` → «площадь/габариты
объекта», `element_type` → «тип работ». Машинные ключи остаются в trace/JSON для отладки, но не
должны попадать в пользовательский текст и следующий модельный комментарий.

С 0.24.0.31 видимый ответ сметного режима разделён на два слоя: `answer` содержит короткую
операторскую сводку с итогом и принятыми позициями, а payload `artifact` содержит полную
сметную расшифровку: позиции, ОЗП/ЭМ/ЗПМ/материалы/прямые/ФОТ/НР/СП/СМР, ресурсы с ценами и
отдельную отметку о неприменённых высотных/производственных коэффициентах.

С 0.24.0.47 auto-чат имеет узкий вход в smeta harness для запросов вида «рассчитать/сметная
стоимость работ + явный объём/площадь/масса/количество». Это не заменяет табличный поиск:
`найди/покажи строки сметы` остаются table/RAG-запросами. Цель — не дать явной заявке на расчёт
позиции уехать в случайные ВОР-строки только из-за слов `сметная стоимость` и `работы`.

## 2. Тариф труда (почему ОЗП ≠ 0)

В базе ФГИС ЦС трудозатраты приходят как **«Средний разряд работы N,M» без кода ресурса** — а без
кода цена не находится, ОЗП был бы 0. ЛЕС закрывает это **read-time**: из наименования выводится
тарифный код `1-100-NM` (`gesn_service._labor_tariff_code`, regex по «разряд N,M»). Эталонный разряд
**2,5 → код `1-100-25`**, цена которого есть в «Сплит-форме» → ОЗП базовых норм ≠ 0.

Граница: **машинист-агрегат** «Затраты труда машинистов» идёт **без разряда** → код не выводим →
строка помечается флагом «нет цены» (а не молча 0). В семени эталона ОТм заданы явной ценой (тариф
по разряду), поэтому ЗПМ эталона точен.

## 3. Как пользоваться (чат-каналы Совушки)

Все функции доступны в чате одной строкой (детерминированные каналы `smeta_chat_service`, 0 LLM,
до RAG). Каналы и примеры:

**Цена ресурса по коду** — «цена `<код>`», «сколько стоит `<код>`»:
```
> цена 91.05.01-017
Краны башенные, г/п 8 т · маш-ч
Сметная цена (текущая): 865.44 руб. (базовая 622.62 × индекс 1.39)
Санкт-Петербург · 2 кв. 2025 · книга …
```
(Сходится с проверенным эталоном кровли до копейки: краны 622.62×1.39=865.44.)

**Нужен ли КАЦ** — «нужен ли КАЦ `<код>`», «есть в ФГИС `<код>`»:
```
> нужен ли кац 01.7.99.99-9999
Кода 01.7.99.99-9999 НЕТ в ФГИС ЦС — нужен КАЦ: ≥3 коммерческих предложения на материал,
выбрать экономичный, цену учесть в смете (Инструменты → КАЦ).
```
Логика: `kac_service.needs_kac` смотрит, **есть ли код в книге цен** ФГИС ЦС (локаль-первый вердикт).

**Коэффициент стеснённости** — «коэффициент стеснённости в городе»:
```
> коэффициент стеснённости город
Коэффициент стеснённости — «<условие>»: к ОЗП ×1.15, к ЭМ ×1.15. …
Применяется к ОЗП и ЭМ позиции (материалы не трогаются).
```
Каталог условий — `config/domain/stesnennost.yaml` (значения типовые, правятся в yaml).

**Сборка позиции от кода ГЭСН** — «собери `<код>` объём N»:
```
> собери ГЭСН12-01-034-02 объём 0.61
Устройство обрешётки с прозорами из брусков · ГЭСН12-01-034-02 · объём 0.61 100 м2
ОЗП 3 750.23 + ЭМ 992.40 + М 83.62 = прямые 4 826.25
ФОТ 4 208.91 → НР 4 587.71 (109%) + СП 2 399.08 (57%) · вид работ: Кровли
ИТОГО по позиции: 11 813.04 руб.
```
Это сквозной **эталон**: код без ресурсов → движок разворачивает норму → цены → НР/СП → 11813.04.
Если норма не в локальной базе — канал добирает её из ФГИС ЦС (бесплатно) или smetnoedelo (с токеном).

**Объектная смета из фразы** — режим `smeta_harness`:
```
> дай смету на объект / раздел / работу
1. Модель возвращает JSON `smeta_work_plan_v1`: объект + 3-6 работ-кандидатов по явно названным
   разделам.
2. `search_norm` подбирает кандидатов ГЭСН из локальной базы.
3. `add_position` считает физический объём кодом, проверяет применимость/единицы/магнитуду и
   переводит в измеритель нормы.
4. Видимый ответ показывает рассчитанную часть, blockers и вопросы; финальный итог появляется
   только когда все ключевые позиции подтверждены.
```
Геометрия, если она нужна формуле, всё ещё грубая: S₁ = S/N, a = √S₁, **P = 4·√S₁**; допущения
выписываются в `assumptions`. Но состав работ не берётся из объектного пресета: модель сама делает
декомпозицию, а код не является “нянькой” состава.

**Тяжёлое ТЗ по массе без ВОР** — fallback для стальных/бронзовых конструкций:

- расчёт по массе остаётся ориентиром `computed_assumed`, не защищаемой ЛСР;
- видимый ответ не показывает служебные `source_ref`/yaml/id ставок как доказательства;
- в ответ добавляются кандидаты ГЭСН из сборника 09 для ручной привязки к ВОР/Приложению 1;
- продолжения текущей сессии используют `retrieval_trace` предыдущего tool-расчёта: фраза
  «учти высотные работы» поднимает массу/ярусы из прошлого ответа и либо применяет явный
  коэффициент (`k=1,15`), либо честно просит высоту/ПОС/нормативное основание.

**Куда это идёт по плану.** Сметные каналы становятся инструментами агент-роутера:
price/kac/stesn/lsr_assemble уже MCP-инструменты; объектная смета идёт через
LLM-рассуждение о составе работ над корпусом норм + те же инструменты-калькуляторы.
Механизм счёта (код) не меняется — меняется кто его вызывает.

С 0.24.0.352 generated `SMETA_SERVICE/**` индексируется не в пользовательский
`TABLE_SMETA_Index`, а в типизированный `SMETA_SERVICE_Index`
(`dataset_scope=system`, `module_id=smeta`). `SMETA_RU_NORM_*` и GESN projection имеют ту же
module ownership. Они добавляются только к smeta-turn и не конкурируют с будущими project ВОР/ЛСР.
Отсутствующие цены отражаются в `pricing_status` и строковых `price_requirements`; они не
останавливают расчёт уже определённых работ/количеств глобально.

Принцип **локаль-first**: запрос сначала бьёт по локальной базе/книге; добор из сети — узкий
fallback с таймаутом ([[local-bases-untrusted-channel]]), сеть недоверенная по умолчанию.
ГЭСН-семя (`config/domain/gesn_seed.yaml`) содержит демо-норму эталона с полными тарифами и
**побеждает базу** при совпадении кода — эталон остаётся точным.

## 5. Принципы

- **ADR-11 — числа считает КОД, не LLM** ([[llm-minimalism-principle]]). Модель первична как
  диспетчер/связующий слой: понимает намерение, держит контекст, предлагает декомпозицию,
  находит недостающие слоты и объясняет результат. Харнесс первичен в расчёте: нормы, цены,
  коэффициенты, ВОР и итог проходят через инструменты/код; число без происхождения не результат.
  Если состав работ уже полный, модель не нужна как “сметчик-калькулятор” — она должна вызвать
  правильные инструменты, проверить применимость и показать blockers/MISSING. Геометрия, разворот
  норм, цены, НР/СП и хвост — детерминированная арифметика.
- **Числа цитируемы и проверяемы.** Каждая величина прослеживается до нормы/книги/Приказа; gold-тесты
  фиксируют эталон 11813.04 (`tests/test_gesn_service.py`, `tests/test_lsr_assembly_service.py`).
- **Знание ≠ веса.** Меняющиеся факты (ставки НР/СП, коэффициенты стеснённости, доменные правила) —
  в редактируемых источниках/role-pack/skill, а не в fine-tune ([[ALGO-smeta-ontology]]).
- НР/СП — из официальных **Приказов Минстроя 812/пр (НР) и 774/пр (СП)**, оба % от ФОТ, по виду
  работ (`config/domain/nr_sp.yaml`, поле `basis` несёт номер пункта Приказа).

## 6. Честные границы

- **Объектных шаблонов/пресетов больше нет как продуктового маршрута.** Новый объект или раздел не
  добавляется if-веткой. Системное улучшение: skill/role-pack для профессии + инструментальный
  подбор норм + deterministic gates.
- **Состав работ model-first.** Модель отвечает за декомпозицию явно названных разделов; код не
  добавляет недостающие разделы “за неё”. Если модель схлопнула объект в одну позицию, это дефект
  prompt/skill/eval, а не повод добавлять ситуационный шаблон.
- **Базовые нормы из parquet несут материалы/машины, но не тариф ОЗП/ОТм** → ОЗП таких позиций = 0
  до загрузки тарифов; смета всё равно собирается на доступном (материалы + машины + НР/СП от ФОТ).
  Полная бухгалтерия (ОЗП≠0) — у норм с тарифом по разряду (как эталон 12-01-034-02 в семени).
- **Машинист-агрегат без разряда** → код не выводим → флаг «нет цены» (не молчаливый 0).
- **Геометрия грубая** (квадрат в плане, P = 4·√(S/N)); сложные обводы/проёмы — допущение, помечается.
- **Подбор кода нормы под произвольную работу ВОР** (наименование → ГЭСН) — отдельный шаг (ретрив по
  базе ГЭСН), пока не автоматизирован.
- **План:** `ГЭСН sqlite light`/нормализованная витрина кандидатов как инструмент подбора норм:
  модель формулирует смысл, витрина отдаёт shortlist, код проверяет единицы/применимость и считает.
